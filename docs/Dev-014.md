# Dev-014: AI-proposed furniture in BitCanvas (LLM → primitive spec → sprite)

[Feature] [Tooling] [Art pipeline] [LLM]

The user wants the game's graphics to come from AI. Pixel-by-pixel drawing is not an option for
either model: Jev (TypeSafe `choice`) only picks from a closed list, and a text LLM places
thousands of coherent pixels badly. What a text LLM does well is write structured descriptions, and
BitCanvas furniture already is one. Each piece in `BitCanvas/pixelart.js` is a list of solids
(boxes, cones, horizontal cylinders, ellipsoids) with roles, ray-traced with the game's exact
projection, light, ramps and outlines. This doc lets an LLM write that list as JSON. Code
validates the JSON and BitCanvas renders it. The model proposes, the code decides (VISION
[Sec. 2], pillar 5).

This is path A, chosen by the user on 23/09/2026. Path B (image diffusion models) is out of scope
[Sec. 12].

Reference: `docs/utils/VISION.md` [Sec. 3], [Sec. 13]; `docs/Dev-012.md` (objects: one facing,
`src/sprites/object/<kind>.png`, heights in whole half-metres, single-tile kinds); `docs/done/Dev-009.md`
(BitCanvas module, File System Access sync, why the game server was rejected *for writing files*);
`CONTEXT.md` (BitCanvas pitfall).

## 2. The furniture spec

### 2.1 Shape

```json
{
  "name": "Pizza oven",
  "description": "Brick dome oven on a wooden stand with an iron door.",
  "height": 3,
  "surface": false,
  "palette": "moss",
  "slots": { "door": ["metal", "gold"] },
  "prims": [
    { "kind": "box", "from": [3, 3, 0], "to": [29, 29, 16], "role": "wood", "pattern": "planks", "axis": 0 },
    { "kind": "blob", "center": [16, 16, 28], "radii": [13, 13, 14], "role": "clay" },
    { "kind": "box", "from": [12, 27, 18], "to": [20, 29, 26], "role": "$door" },
    { "kind": "choose", "options": [
      [ { "kind": "cyl", "cx": 22, "cy": 10, "z0": 36, "z1": 48, "r0": 2, "r1": 2, "role": "metal" } ],
      [ { "kind": "cyl", "cx": 10, "cy": 22, "z0": 36, "z1": 46, "r0": 2.5, "r1": 2, "role": "clay" } ]
    ] }
  ]
}
```

Primitive fields, matching the `pxBox`, `pxCyl`, `pxLog` and `pxBlob` constructors:

| `kind` | Geometry fields | Allowed `pattern` |
|---|---|---|
| `box` | `from`, `to` (3 numbers each) | `planks` (needs `axis` 0–2), `panel`, `quilt`, `stripes`, `spine` (optional `band`) |
| `cyl` | `cx`, `cy`, `z0`, `z1`, `r0`, `r1` (vertical cone or cylinder) | `staves`, `pleats` |
| `log` | `cy`, `cz`, `r`, `x0`, `x1` (horizontal cylinder along x) | `planks` |
| `blob` | `center`, `radii`, optional `axes` (3 unit, orthogonal vectors) | none |
| `choose` | `options`: 2–4 lists of 1–20 primitives (no nested `choose`) | n/a |

Optional on every solid: `pattern`, `width` (1–16), `tone` (−2 to 2), `axis`, `band`.

### 2.2 Semantics

- `role` is a `PIXEL_ROLES` key (`wood`, `woodDark`, `woodLight`, `metal`, `gold`, `fabric`,
  `sheet`, `pillow`, `blanket`, `blanketLight`, `glow`, `leaf`, `stem`, `soil`, `clay`, `ceramic`,
  `fruit`, `hole`, `book0`–`book3`) or `$name`, a slot declared in `slots`.
- `palette` (optional) is one of `meadow`, `emerald`, `moss`, `autumn` (Oak, Walnut, Pine,
  Driftwood). BitCanvas selects it when the piece loads. The user can still change it.
- Randomness, in this exact order, from `pxRandom(variantSeed)`: first each slot in declaration
  order picks `options[Math.floor(random() * options.length)]`, then the primitives are walked
  in order, and each `choose` picks its option the same way when reached. With
  `"slots": { "trim": ["metal", "gold"] }`, this equals the built-in chest's
  `random() < 0.5 ? 'metal' : 'gold'`, which [Sec. 10] step 2 relies on.
- Extent is always the full tile, `from [0, 0, 0]`, `to [32, 32, height × 16]`, so every AI sprite
  of the same height has the same size and anchor (64 + 2 by 32 + height × 16 + 2 px, with the
  outline margin).

### 2.3 Validation rules (server and BitCanvas)

The server rules are the contract. The BitCanvas mirror (`pxValidateSpec`) implements the same
list and returns the same messages. Each failure is one message naming the path
(`prims[3].to[2]: 52 is above height 3 (48 units)`).

1. The JSON parses and has exactly the fields of [Sec. 2.1]. Unknown fields are errors.
2. `name` is 1–32 characters and contains at least one ASCII letter; `description` is at most 200.
3. `height` is an integer from 1 to 6. `surface` is a boolean.
4. `slots`: at most 4, names `^[a-z][a-zA-Z0-9]*$`, 2–4 roles each, all `PIXEL_ROLES` keys.
5. Every `role` is a `PIXEL_ROLES` key or a declared `$slot`.
6. Every number is finite (Python's `json` turns `1e999` into `inf`). Boxes have `from < to` on every
   axis, with at least 0.5 units. Cones have `z1 − z0 ≥ 0.5`, radii `≥ 0` with at least one `≥ 0.5`.
   Logs have `x1 − x0 ≥ 0.5` and `r ≥ 0.5`. Blob radii are `≥ 0.5`. Blob `axes` are unit length
   within 0.01 and pairwise orthogonal within 0.05. The pixel renderer's normals assume both.
7. Each `pattern` is allowed for its kind [Sec. 2.1]. `planks` on a box needs `axis`.
8. `choose` is not nested. Each option has 1–20 primitives.
9. There are at most 80 primitives in total, counting every option of every `choose`.
10. Every primitive's bounds (the same bounds `pxPrepare` computes) lie inside
    `[0,32] × [0,32] × [0, height × 16]`, with a tolerance of 0.01.
11. Height fits: the highest top over all primitives is `> (height − 1) × 16`. The declared height
    is the piece's rounded-up size, not a loose ceiling.
12. Surface: when `surface` is true, the highest top among the primitives outside `choose`
    equals `height × 16` within 0.01, and no `choose` option goes higher.
13. Grounded: at least one primitive outside `choose` has its bottom at `z ≤ 0.5`.

## 3. Server

### 3.1 `server.llm` (new module, `server/src/etherbound/llm/`, v0.0.0 → v0.0.1)

The OpenRouter client that Phase 3 will reuse. It has no art knowledge.

- `openrouter.py`: `class OpenRouterClient` with
  `async def complete(self, messages: list[ChatMessage], *, model: str, reasoning: bool, max_tokens: int, temperature: float) -> Completion`.
  - `POST {base_url}/chat/completions` through one shared `httpx.AsyncClient`, closed in the app
    lifespan. Headers: `Authorization: Bearer <key>` and `X-Title: EtherBound`.
  - The payload carries `reasoning` **only** when `reasoning=True`.
    `build_payload(...)` is a pure function so tests can assert it.
  - `Completion` holds `text` (the first choice's content), `usage` (prompt and completion tokens,
    when present) and `latency_ms`.
  - Errors: `LlmUnavailable` (timeout, connection error, 5xx, 429) and `LlmRejected` (other 4xx,
    or no content). Messages never include the key.

### 3.2 `server.artgen` (new module, `server/src/etherbound/artgen/`, v0.0.0 → v0.0.1)

- `spec.py`: Pydantic models `FurnitureSpec`, `Box`, `Cyl`, `Log`, `Blob` and `Choose`, discriminated
  by `kind`, all with `extra="forbid"`. `validate_spec(raw: str) -> FurnitureSpec | list[str]`
  applies [Sec. 2.3] and returns every error, not only the first. `PIXEL_ROLES_KEYS` is a constant
  here, with a test asserting it matches the keys in `pixelart.js` (the test reads the file with a regex).
- `examples/chest.json` and `examples/lamp.json`: the built-in chest (trim as a slot) and the lamp
  (one fixed shade size), transcribed by hand from `pixelart.js`. They are few-shot examples in the
  prompt and fixtures in tests.
- `prompt.py`: `SYSTEM_PROMPT` [Sec. 5] and `build_messages(description, previous, instruction, errors)`.
- `service.py`: `class ArtgenService` with
  `async def furniture(description, previous=None, instruction=None) -> ArtgenResult`:
  build the messages, call the client, strip one optional code fence, validate. If invalid, append
  the answer and a user message listing the errors, then retry (at most 2 repairs). It returns
  `ArtgenResult(spec, model, repairs, usage)` or raises `ArtgenInvalid(errors, last_text)`.
  It logs one line per call on `etherbound.artgen`: model, latency, tokens, and valid or the number
  of errors. It never logs prompts in full or the key.

### 3.3 `server.app` (+0.0.1)

- `config.py`: `openrouter_api_key: SecretStr | None = None`,
  `openrouter_base_url: str = "https://openrouter.ai/api/v1"`, `artgen_model: str | None = None`,
  `artgen_reasoning: bool = False`, `artgen_timeout_s: float = 90` (> 0),
  `bitcanvas_dir: Path | None = None` (None means `<repo>/BitCanvas`).
- `app.py`: create the client and service in `create_app` and store them on `app.state.artgen`
  (None when the key or the model is missing). Close the client in the lifespan. Mount
  `StaticFiles(directory=bitcanvas_dir, html=True)` at `/bitcanvas` when the folder exists;
  otherwise log a warning and skip the mount.
- New `routes/artgen.py`, included with `include_in_schema=False`. It is a dev tool, not part of
  the game client's contract, so `schema.json` and `schema.d.ts` do not change:
  - `POST /api/artgen/furniture`, body
    `{ description: str (1–500), previous: FurnitureSpec | None, instruction: str (1–300) | None }`,
    where `instruction` is required when `previous` is set.
  - `200 { spec, model, repairs }`. `503 { detail: "artgen not configured" }` when there is no key
    or model. `502` on `LlmUnavailable` or `LlmRejected`. `422 { errors, last_text }` on
    `ArtgenInvalid`.
- `server/pyproject.toml`: move `httpx>=0.28,<1` from the dev group to `dependencies`.

## 4. BitCanvas (`bitcanvas`, +0.0.1)

### 4.1 `pixelart.js` and `furniture.js`

- In `furniture.js`, extract `pxMeasure(piece)` from the sizing loop and
  `renderPixelPiece(piece, ramps, seed, options)` from `renderPixelFurniture`.
  `renderPixelFurniture(key, …)` becomes a one-line wrapper. Built-in output stays byte-identical
  [Sec. 10] step 1.
- `pxValidateSpec(spec) -> string[]`: the [Sec. 2.3] mirror.
- `pxPieceFromSpec(spec) -> piece`: `{ description, extent, build(random) }`. `build` resolves the
  slots, walks the primitives, resolves `choose` [Sec. 2.2] and calls the existing constructors in
  `pixelart.js`, passing `pattern`, `axis`, `width`, `tone`, `band` and `axes` (default `PX_AXES`).
  Then `pxMeasure(piece)`.

### 4.2 `app.js` and `index.html`

- **Piece registry.** `aiPieces` maps `key` to `{ recipe, piece }`. Every read of
  `FURNITURE[state.furniture]` (`currentSize`, `furnitureInfo`, `updateSpecText`, `drawPreview` twice,
  the TOP export) goes through a new `currentPiece()`. For an AI key, `currentPiece()` returns the
  spec's name and description, `corner: 'AI PIECE'` and the pixel piece. AI pieces are pixel-only:
  the VOXEL style button is disabled and the style is forced to `pixel` while one is selected.
- **Keys.** Lowercase ASCII slug of `name` (`[a-z0-9_]`, at most 32 characters). If it collides with
  a built-in or a loaded AI key, append `_2`, `_3` and so on.
- **List.** In the FURNITURE tab, after the built-ins, an `AI` separator and one row per AI piece:
  icon `✧`, name, meta `object/<key>`. Arrow keys include these rows.
- **Generate panel** (`furniture-only`, top of the generator panel), following `STYLEGUIDE.md`:
  - `DESCRIBE`: a textarea of at most 500 characters and a `GENERATE` button.
  - When an AI piece is selected: `REVISE`, a textarea of at most 300 characters and a `REVISE`
    button that sends `previous` + `instruction`. The result replaces the piece under the same key
    and appends the instruction to `recipe.prompt.revisions`.
  - While a request is in flight, the buttons read `GENERATING…` and are disabled. The feed shows
    `act` on success (`Pizza oven ready · 1 repair`), `warn` on 422 (first 3 errors, plus a
    `Download answer` link with `last_text`), and `fail` on 502 or when the server is unreachable.
  - From `file:`, the panel shows the hint
    `Generate needs the server: open http://127.0.0.1:8000/bitcanvas/` and the buttons are disabled.
  - A 503 shows `Set ETHERBOUND_OPENROUTER_API_KEY and ETHERBOUND_ARTGEN_MODEL in .env`.
- **Variant pick.** The 4 variants render as today. Clicking one in the preview selects it for
  sending (default: variant 1). The selection is stored in the recipe.
- **Send to game** is enabled for pixel furniture (built-in and AI). It writes
  `object/<key>.png` (the selected variant, cropped from the atlas) and, for AI pieces,
  `object/<key>.json`. The destination line reads `→ sprites/object/ <key>.png + <key>.json`.
  Generalize `BitCanvasGameSync.send` to take `(folder, files: { name, canvas | text }[])`; the
  terrain call passes its two canvases. `validateFolder` is unchanged.
- **Recipe** (`format: 1`):
  `{ format, key, spec, render: { seed, variant, paletteKey | null, ramp, brightness, shadow }, prompt: { description, revisions[] }, model, repairs, created }`.
  `ramp` is the 8-step wood ramp actually used, so a random palette also reproduces. `created` is
  an ISO date (wall clock is fine: this is not the simulation).
- **Loading.** On start, if a folder handle is stored **and** `queryPermission` is already
  `granted` (no prompt), read `object/*.json`, validate each one, and add the valid ones. Invalid
  files give one `warn` line each. An `IMPORT` button (file input, `.json`) loads a recipe on any
  browser, including `file://`. `RECIPE` downloads the current AI piece's recipe.
- Opened from `http://127.0.0.1:8000/bitcanvas/`, the File System Access handle is stored per
  origin, so the `sprites` folder is picked once more there.

## 5. The prompt

`SYSTEM_PROMPT` is plain English and states, in this order:

1. Its job: design one piece of furniture or prop for an isometric pixel-art life sim as a JSON
   spec. Output only the JSON, with no prose and no code fence.
2. Space: 1 unit = 1/32 m on every axis. The tile is 32 × 32 units and `z` is up. The camera
   sees the `+x`, `+y` and top faces. The front of a piece faces `+y`, and the `+x` side is also
   visible. Keep 2–3 units of margin from the tile edge unless the piece fills it (a crate).
3. Real-world sizes: seat height about 14 units (0.45 m), table height 24 (0.75 m), counter 29
   (0.9 m), door handle 30. Legs and rails are at least 2 units thick, or they vanish at this
   resolution.
4. The schema [Sec. 2.1] and the rules [Sec. 2.3], verbatim from a shared constant (the validator
   and the prompt read the same limits).
5. The role table with one line of meaning each (`hole` is a dark opening, `glow` emits light,
   `sheet` is pale cloth, and so on) and the pattern table with where each one reads well.
6. How to vary: declare 1–2 slots or `choose` groups so the four variants differ, never random
   numbers.
7. The two examples, `chest.json` and `lamp.json`, each with its one-line description.

A generation request's user message holds the description. A revision sends the previous spec as
the assistant turn and then the instruction ("Revise the spec: …"). A repair sends the errors
("Your JSON broke these rules: … Return the full corrected JSON.").

## 10. Acceptance

1. **Byte parity.** Before any edit, after the `gamesync.js` fix, render the 8 built-in pieces
   (4 variants, seed `A17F3C`, first palette, brightness 58, shadow on) and the 7 terrain materials'
   14 sheets headlessly, as in Dev-011 [Sec. 4]. After the change, all SHA-256 hashes match.
2. **Spec parity.** `examples/chest.json` loaded through `pxPieceFromSpec` renders the same 4
   variants as the built-in chest when the extent is overridden to the chest's. Hashes match.
   This proves that slots, patterns and the constructors map one to one.
3. **Server tests** (`uv run pytest`):
   - `test_artgen_spec.py`: both examples are valid. One fixture per rule in [Sec. 2.3] fails with
     that rule's message. A spec breaking three rules reports all three.
   - `test_artgen_service.py`, with a fake client: valid on the first call (`repairs = 0`);
     invalid then valid (`repairs = 1`, the second call carries the error list); three invalid
     answers raise `ArtgenInvalid`; a fenced answer parses; a non-JSON answer counts as invalid.
   - `test_llm.py`: `build_payload` has no `reasoning` key when disabled and has one when enabled.
     The key never appears in the text of a raised error.
   - `test_api.py`: 503 when unconfigured; 200 and 422 through a fake `app.state.artgen`;
     `GET /bitcanvas/` serves `index.html`; `/api/artgen/furniture` is absent from `openapi()`.
   - `ruff`, `ruff format --check` and `pyright` pass; `npm run check:web` shows no schema diff.
4. **file:// (manual).** `npm run bitcanvas` opens BitCanvas, all 7 terrain materials and 8 pieces
   render, Generate shows the hint, and IMPORT of each invalid fixture gives a `warn` without adding
   a row.
5. **Generate (manual).** With the key and model set and the server running,
   `npm run bitcanvas:ai`, then "brick pizza oven on a wooden stand": an `AI` row appears with 4
   distinct variants and the feed says how many repairs. "Make the chimney taller" revises it under
   the same key.
6. **Send and reload (manual).** Send writes `src/sprites/object/pizza_oven.png` (the selected
   variant, 66 × 82 px for height 3) and `pizza_oven.json`. After a page reload the piece is back in
   the list from the folder. Deleting the recipe's `spec` field gives a `warn` on the next load.
7. **Failure paths (manual).** With the server stopped, Generate gives `fail` and no crash. With
   the model unset, it shows the 503 hint.
8. **Benchmark** [Sec. 6] recorded here.

## TL;DR

An LLM on OpenRouter writes furniture as a JSON list of the primitives BitCanvas already
ray-traces: boxes, cones, logs and ellipsoids with roles, patterns, seeded slots and `choose`
groups. The server holds the key, validates each answer against 13 rules, and returns errors to the
model for at most 2 repairs. BitCanvas, served by the game server at `/bitcanvas/`, generates and
revises pieces, renders 4 seeded variants, and sends the chosen one to `src/sprites/object/` with a
recipe beside it. Built-in sprites stay byte-identical, the game never calls a model for art, and
`file://` BitCanvas still works. The parse error was fixed independently by Fix10. Dev-014 lands
after Dev-012, adds `server.llm` and `server.artgen`, and the model is chosen by an 8-piece benchmark.
