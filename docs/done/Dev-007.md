# Dev-007: Op vocabulary, generated menus and the first world ops (Server + Web)

[Feature] [Engine] [World] [UI] [Architecture]

Settles the open "Op list" question and turns the right-click menu from a stub into the real
action surface:

- The rename of "verb" to **op** (operation) in code and protocol.
- The first vocabulary of 58 generic ops, stored as data.
- Menus generated from the handlers and the target's properties.
- Ops that take game time, called **activities**.
- Four ops that work on today's world without any new primitive: `inspect`, `wait`, `dig`
  and `climb`. `move` stays as it is.

Digging needs one change to the world model. Otherwise the strata would sink along with the
surface [Sec. 1].

Reference: `docs/utils/VISION.md` [Sec. 5] (world model), [Sec. 6] (primitives), [Sec. 7] (ops ×
properties, generated menus) and [Sec. 15] (Phase 1); `docs/done/Dev-005.md` (pipeline, events);
`docs/utils/STYLEGUIDE.md` [Sec. 8] (context menu), [Sec. 11] (feed) and [Sec. 16] (keyboard);
`CONTEXT.md`.

**Depends on** `docs/Fix02.md` H3 (the stale `h` on load). Land it first. Otherwise an old save
can freeze Niko in a hole he just dug.

## 1. Decisions to approve

| Topic | Decision | Why |
|---|---|---|
| Naming | The vocabulary entry is an **op** (operation), not a "verb". An **action** is one submitted use of an op (op + target + modifiers). Code and protocol say `op` everywhere: `engine/ops/`, `ops.toml`, `OpHandler`, `OpSpec`, the `op` discriminator, `MenuResponse.ops`, `.menu .op`. Docs in `docs/done/` keep the old word | More technical, and it separates the vocabulary entry (`dig`) from the submitted action (`DigAction`). Renaming now touches only `move` and the `/api/menu` stub; after this doc it would touch 58 entries. VISION, STYLEGUIDE, AGENTS, PENDING, Fix01 and Fix02 already use it (22/09/2026) |
| Vocabulary | The 58 ops of [Sec. 2] are the v1 vocabulary. It is a living list: it changes through a Dev doc, never ad hoc | Closes the `PENDING.md` question. VISION [Sec. 6] asks for 40 to 60 |
| Crimes are not ops | `steal` is `take` on something another actor owns; `murder` is `hit` until the target is dead; `lie` is `tell` with a `false` modifier. Law tags the act from ownership and context | Pillar 1. VISION [Sec. 9]: laws are data rows on `{op/tag, context}`. A crime op would hardcode what the law system must decide |
| Ops as data | `server/src/etherbound/engine/ops.toml` lists every op (key, label, group, target kinds, tags). A handler in code attaches behaviour to a key. An op with no handler is never offered | The vocabulary is readable and reviewable as data. Adding behaviour never adds a vocabulary entry by accident |
| Menus | The server builds each entry from `applies` (show it at all) and `validate` (available, or the reason it is not), and attaches the exact `action` to submit. The client renders it and sends back what it got | VISION [Sec. 7] and STYLEGUIDE [Sec. 8]: generated, never authored. An op that exists but cannot be done now is shown with its reason, not hidden |
| Activities | An op that takes game time starts an **activity** on the actor: one at a time, stored on the actor, progressing only through clock ticks. Its effects are applied **at completion**, after re-validating. Any new accepted action interrupts it, except a zero-length move, which is not an action. Interrupting loses the progress | Real life: digging takes half an hour, and walking away stops it. Effects at completion keep the world model simple. Progress that survives interruption is a later refinement |
| Dig model | Digging lowers the tile's heightmap by 0.5 m per activity, and a per-tile `dug` count anchors the strata to the **original** ground | Today strata depth is measured from the current `ground_h`, so a lowered surface drags every layer down with it and nobody ever reaches clay or rock. The heightmap already models pits (the park pit), and the `LEVEL_VOID` flag works per 3 m band, far too coarse for 0.5 m |
| Hand digging | Until tools exist, every actor digs as if with a shovel: `ceil(30 × dig_cost)` game minutes per 0.5 m (topsoil 24, dirt 30, clay 42). Anything with `dig_cost > 2.0` (concrete, rock, asphalt) is shown as "too hard to dig by hand" | About 0.5 m³ an hour by shovel is the real-life rate. Tools come with the objects doc and will scale this |
| Climb | New vertical link: `climb` onto or down from an orthogonal neighbour 1 m or 1.5 m away (Δ`h` 2 or 3). It takes 1 game minute and has no roll yet | A person climbs a 1 m ledge. Without it, a 1 m hole is a trap. Rolls arrive with the character sheet. Changes VISION [Sec. 5], which says ladders are the only link above 0.5 m |
| Reach | `dig` and `climb`: the actor's own tile or an orthogonal neighbour, with no wall on the shared edge. `dig` also needs the ground within ±1 m of the actor's `h`. `inspect`: 30 m, with no line-of-sight check yet | Close reach is real life. Line of sight arrives with perception and witnesses |
| Inspect | Instant, changes nothing and **emits no event**. It returns a line: material, height, dug depth and visible properties. It never reveals strata | Pillar 3: Niko sees the surface, not the underground. Observers noticing someone looking comes with witnesses |
| Activity notices | The hub broadcasts one `activity` message when one of Niko's activities finishes, carrying its outcome. General event streaming stays deferred | Otherwise the player never learns why a dig failed. It is scoped to one message type so it does not grow into the deferred event stream |
| No rolls | None of the four ops rolls dice. The roll formula, stats, skills and RNG stream persistence stay deferred to the character-sheet doc | None of these ops is uncertain enough to need one, and rolls need stats that do not exist yet |

### 3.2 Vocabulary and handlers (`server.engine`)

`engine/ops.toml`, one entry per row of [Sec. 2], in that order:

```toml
[[ops]]
key = "dig"
label = "Dig"
group = "matter"
targets = ["tile"]
tags = ["labor", "noisy"]
```

`engine/ops/catalog.py` loads it once and validates it: keys are unique snake_case ASCII,
targets come from the five kinds, and tags are non-empty. `targets` holds only the primary
target kinds: `move` has `targets = []` (it is never a menu entry), and a secondary argument such
as the `actor` of `give` waits for the doc that adds it. It exposes `OpSpec` and
`catalog() -> tuple[OpSpec, ...]`.

`OpHandler` (`engine/ops/base.py`) becomes:

```python
class OpHandler(Protocol):
    op: ClassVar[str]
    def applies(self, ctx: ActionContext, target: Target) -> bool: ...          # show in the menu at all
    def build(self, ctx: ActionContext, target: Target) -> Action: ...          # the action the menu offers
    def validate(self, ctx: ActionContext, action: Action) -> str | None: ...   # reason, or None
    def duration(self, ctx: ActionContext, action: Action) -> int: ...         # game minutes; 0 = instant
    def resolve(self, ctx: ActionContext, action: Action) -> Resolution: ...   # instant ops
    def complete(self, ctx: ActionContext, action: Action) -> list[Event]: ... # activities, at the end
```

- `Resolution` holds `events: list[Event]` and `text: str | None`.
- `register()` also raises if the key is missing from `ops.toml`.
- `MoveHandler` keeps its current behaviour. `applies` is `False`, since movement is never a
  menu entry, and `duration` is `0`.

### 3.3 Targets and actions (`engine/actions.py`)

```python
class SelfTarget(BaseModel):  kind: Literal["self"] = "self"
class TileTarget(BaseModel):  kind: Literal["tile"] = "tile"; x: int; y: int; h: int
Target = Annotated[SelfTarget | TileTarget, Field(discriminator="kind")]

class InspectAction(BaseModel): op: Literal["inspect"] = "inspect"; target: TileTarget
class WaitAction(BaseModel):    op: Literal["wait"] = "wait"; target: SelfTarget = SelfTarget()
class DigAction(BaseModel):     op: Literal["dig"] = "dig"; target: TileTarget
class ClimbAction(BaseModel):   op: Literal["climb"] = "climb"; target: TileTarget
Action = Annotated[MoveAction | InspectAction | WaitAction | DigAction | ClimbAction, Field(discriminator="op")]
```

`ActionResult` gains `text: str | None = None` and `activity: ActivityState | None = None`.

### 3.4 Activities (`server.engine`, `server.db`)

```python
class ActivityState(BaseModel):
    op: str
    action: dict[str, Any]    # the submitted action, re-parsed with the Action adapter at completion
    started_minute: int
    ends_minute: int
```

- It is stored in the new nullable JSON column `actor.activity`.
- `submit`, after the paused check:
  1. A zero-length `move` returns accepted and does nothing (it does not interrupt).
  2. Validate. A rejection changes nothing, including a running activity.
  3. If the actor has an activity: clear it and emit `activity.finished`
     (`outcome = "interrupted"`, `reason = "<new op>"`).
  4. `duration == 0`: `resolve`, which gives events and text.
  5. Otherwise store the activity with `ends_minute = game_minute + duration` and emit
     `activity.started`.
- `advance_time`, after incrementing the minute, in the same lock and transaction: go through
  actors by `id` whose `activity.ends_minute <= game_minute`. Re-parse the action and validate
  it again:
  - If it now fails: `activity.finished` (`failed`, with the reason).
  - Otherwise: the events from `complete(...)`, then `activity.finished` (`completed`).
  - Clear the activity in both cases.
- A paused clock sends no ticks, so activities freeze with the world. x3 and x10 speed them up.

### 3.5 Menus (`server.engine`, `server.app`)

`WorldEngine.menu(actor_id, x, y, z) -> MenuPayload`:

- It resolves the tile target exactly as `/api/menu` does today (pick the standing surface for
  `z`) and keeps today's `target` label (`Asphalt · 1 m`).
- Candidates are `TileTarget(x, y, h)` and, if the tile is the actor's own tile, also
  `SelfTarget()`.
- For every catalog op that has a handler, for every candidate its `targets` allow: if
  `applies(...)`, add an entry. The entry holds `op`, `label`, `tags`, `action = build(...)`,
  `available = validate(action) is None` and `reason`.
- Entries follow catalog order. It reads only; no lock is needed.

`GET /api/menu?x&y&z` returns
`MenuResponse { x, y, z, target: str, ops: list[MenuEntry] }`, where
`MenuEntry { op, label, tags: list[str], available: bool, reason: str | None, action: Action }`.
The `menu` query is computed for `PLAYER_ID`, as the client only plays Niko.

### 3.6 The four ops

Constants live in `engine/ops/`: `HAND_DIG_MAX_COST = 2.0`, `DIG_MINUTES_PER_COST = 30`,
`CLIMB_MINUTES = 1`, `WAIT_MINUTES = 15` and `INSPECT_RANGE_M = 30`.

**`inspect`** (tile, instant)
- Applies to any loaded tile with a standing surface.
- Reasons: `nothing to see` (no standing surface at `target.h`), `too far to see` (more than
  30 m, centre to centre).
- Text: `<Material> · <h/2> m`, then `· dug <dug/2> m` if `dug > 0`, then the visible properties
  among `diggable` (only when `dig_cost ≤ 2`), `flammable` and `liquid`. For example:
  `Grass · 1 m · diggable, flammable`.

**`wait`** (self, 15 min)
- Applies to `SelfTarget`. No reasons.
- `complete` returns no world event; only `activity.finished`.

**`dig`** (tile, `ceil(30 × dig_cost)` min of the removed material)

Let `g = ground_h` and `d = dug`, so the original ground is at `g + d`. The removed volume sits at
`h = g - 1`, material `R = stratum(d + 1)`. The exposed floor sits at `h = g - 2`, material
`S = stratum(d + 2)`, where depth is measured from the original ground.

- Applies when the target is the tile's ground surface (`target.h == g`, so never a floor or a
  roof) and the surface material is `diggable`. That hides asphalt, water and glass. Concrete and
  rock stay visible, shown as too hard. (An earlier draft said "or when `R` is": that offered
  `dig` on the road, since topsoil lies under the asphalt.)
- Reasons, in this order:
  1. `out of reach`: not the own tile or an orthogonal neighbour, or a wall is on the shared
     edge, or `|g - actor.h| > 2`.
  2. `floor in the way`: a level on the tile has `floor_h != NO_FLOOR` and `floor_h >= g`.
  3. `too hard to dig by hand`: the surface material or `R` has `dig_cost > 2.0`, or `R` is not
     diggable.
  4. `hollow below`: the volume at `g - 1` is not solid (a basement void).
  5. `hard layer below`: `S` is not walkable.
  6. `someone is standing there`: another actor stands on the tile at `g`.
- `complete`:
  - `grid.lower_ground(x, y)` sets `ground_h = g - 1`, `surface_mat = S`, `dug = d + 1` and
    `revision + 1`.
  - Persist the chunk row.
  - Every actor standing on that tile at `h = g` goes to `g - 1`, and `z` is recomputed.
  - Events: `terrain.dug`, then `actor.moved` (`mode = "lowered"`) for each lowered actor, then
    `chunk.changed`.

**`climb`** (tile, 1 min)
- Applies when the target is an orthogonal neighbour with at least one standing surface, and none
  of its surfaces is within ±1 `h` of the actor. If it were, the actor would simply walk.
- Reasons:
  - `out of reach` when the target is not an orthogonal neighbour (a crafted action).
  - `nothing to stand on` when the target tile has no surface at `target.h` any more.
  - `too high to climb` when no surface is within Δ`h` 2–3.
  - `wall in the way` when there is a wall on the shared edge at the actor's `h` or at the
    target's `h`.
- `build` targets the surface nearest to the actor within Δ`h` 2–3.
- `complete` puts the actor at the target tile's centre, at that surface's `h`, recomputes `z`,
  and emits `actor.moved` with `mode = "climb"`.

### 3.7 World changes (`server.world`, `server.db`)

- `Chunk` gains `dug: tuple[int, ...]` (1024 × uint8, zeros by default), with a blob round-trip.
- The test generator leaves it at zeros. Natural pits and ponds stay plain heightmap.
- `WorldGrid._underground_material` measures depth as `ground_h + dug - h`. Every caller
  (`solid_at`) inherits this.
- New `WorldGrid.stratum_at(x, y, depth_from_original) -> material_id`, used by `dig`.
- New `WorldGrid.lower_ground(x, y) -> Chunk`. It replaces the frozen chunk in the grid and
  returns the new one. Only the engine calls it.
- `ChunkPayload` and the chunk messages do **not** carry `dug`. The client never needs it.
- Migration `0004_dig_activity`: `chunk.dug` (nullable `LargeBinary`, where NULL means all zeros) and
  `actor.activity` (nullable JSON). The downgrade drops both. Existing saves need no wipe.

- Client → server: `ActionMessage { type: "action", sequence, action: Action }`. The hub

### 3.10 Web client

- **`web.net`:**
  - **Input fix (found while implementing).** Since v0.1.0 `sendInput` has sent
    `{direction, vector}` instead of `dx`/`dy`, so the server rejects every browser input with a
    validation `error` and never moves Niko; only the client prediction moves. It also sends only
    when the direction changes, while the server moves 0.2 m per input (`delta_seconds = 1/20`).
    `sendInput` now sends `{type: "input", sequence, dx, dy}`, and `web.game` repeats it every
    50 ms while a direction is held, plus one zero vector on release. Without this, `dig` and
    `climb` act on a Niko still standing at spawn, and the idle resync below snaps him back there.
  - `sendAction(action)` returns the sequence.
  - `onResult` and `onActivity` listeners.
  - `ActorState.activity`.
  - `MenuOp` ([Sec. 3.1]) becomes the generated `MenuEntry` type; drop the hand-written parsing
    in `readOps` in favour of the schema type.
- **`web.ui`:**
  - Clicking an available entry sends `entry.action` and closes the menu.
  - Arrow keys move `.focus`, Enter picks and Esc closes (STYLEGUIDE [Sec. 8]).
  - Unavailable entries keep `.off` and show `reason` in `.why`. Labels are uppercased by CSS
    (`.menu .op`); the reason keeps its case.
  - Each entry is a `.op` button. Its extra class comes from `tags` (`ether`, `illegal` when present).
  - The feed shows:
    - `result.text` as a `.seen` item.
    - A rejection as `CAN'T <OP> · <reason>` in `--yellow`.
    - A start as `<OP> · <n> MIN`.
    - The `activity` message: `completed` gives `<OP> DONE`; `failed` gives
      `<OP> FAILED · <reason>` in `--red`; `interrupted` gives nothing, since the player
      caused it.
  - Telemetry gets an `ACT` row, `DIG · 12 MIN`, computed as `ends_minute - gameMinute`, shown
    only while there is an activity.
  - Rename the feed label from `INPUT ECHO` to `FEED`.
- **`web.game`:**
  - On a chunk update, where the store already had the chunk, redraw that chunk and its loaded
    orthogonal neighbours, so the cliff lines on the border follow.
  - On each tick, if the player is idle (zero direction, no unacknowledged input) and the
    server's `x/y/h` differ from the prediction (more than 0.05 m, or any `h`), reset the
    prediction to the server position. Climbing and being lowered by a dig move Niko without
    an ack. Add `ClientPrediction.idle()` if it does not exist.

## 4. Traps

1. **Strata anchoring.** Every call site that computes underground material must add `dug`. If
   one is missed, a dug tile reports the wrong material or solidity. Grep for `ground_h -` in
   `grid.py`.
2. **Frozen chunks.** `Chunk` is immutable. `lower_ground` must replace it in `grid._chunks`, and
   the engine must persist the same object it put in the grid.
3. **Revision race.** Push a changed chunk only to connections that already know it. The others
   get the new revision when they walk near. Never lower a known revision.
4. **Interrupt only after validation.** A rejected action (paused, out of reach) must leave the
   running activity alone.
5. **The zero-length input.** The client sends a zero vector when keys are released. It must not
   interrupt an activity, or releasing WASD right after clicking `dig` cancels it.
6. **Completion order.** Resolve completions in actor-`id` order, inside the tick's lock and
   transaction, before `clock.ticked` is enqueued. Replay depends on it.
7. **Standing after a dig.** If the digger stands on the tile, move them down in the same
   transaction. Otherwise they float 0.5 m above the new ground and the standing rule freezes
   them (the same failure as Fix02 H3).
8. **The menu is a read.** `menu()` must not take the engine lock or write. It may race a tick;
   `submit` validates again anyway.
9. **Schema churn.** `MenuResponse.verbs` (`list[str]`) becomes `ops` in [Sec. 3.1] and then
   entries in [Sec. 3.5]. Replace the client's defensive parsing; do not keep either old shape.
10. **Half a rename.** Server and client change the menu field in the same commit, or the menu
    comes back empty. Leave `docs/done/` alone; it is history.
11. **The server never saw WASD.** Every earlier GUI acceptance of walking checked the prediction
    only. After the input fix [Sec. 3.10], walking must be rechecked against the server
    (`GET /api/game/state` after a walk).

## TL;DR

Renames "verb" to **op** first, in its own commit with no behaviour change. Then closes the
op-list question with a 58-op v1 vocabulary kept as data in `ops.toml`. Crimes like stealing are
ordinary ops judged by law, not ops of their own. The right-click menu
becomes generated: every handler says whether it applies, whether it is available and why not,
and hands the client the exact action to send. Ops that take time are activities: stored on
the actor, advanced by clock ticks, interrupted by any new action, applied at completion after
re-validation.

Four ops work on today's world: `inspect` (instant, a text line), `wait` (15 min), `dig`
(0.5 m per activity) and `climb` (1–1.5 m, 1 min). Dig time comes from the material, and
anything harder than clay is "too hard to dig by hand". Dig is backed by a per-tile `dug` count
that keeps the strata anchored to the original ground (migration `0004`). The world model gains
a 1–1.5 m climb, which updates VISION. No rolls yet.

Six server modules and three web modules get one bump each. Land Fix02 H3 first.

Implementing it turned up an older bug: the browser had never sent `dx`/`dy`, so WASD never
moved Niko on the server. The client now sends them, repeated at 20 Hz while a key is held.
