# Dev-005: HUD visual polish and information density

[Feature] [UI] [Polish]

Dev-004 put the HUD on the Figma grid; it is correct but bare. The captures show a left menu whose
buttons overflow their column, a header of tiny controls beside a large clock, a status column that
holds one small `CARRY` box, a one-line feed, a debug console that spills over the footer and text
in a generic sans. This plan keeps the grid and every contract, and raises the look and the useful
information on screen: Niko's terminal HUD (the layers in `STYLEGUIDE.md` [Sec. 1] are unchanged), built only
from sim data already in `WorldFrame` and the menu payloads.

## 1. Findings

Read from the 2560×1440 captures of Dev-004 (`spawn-x2.png`, `build-walls.png`, `dev-console.png`)
and from `game/ui/`. Not yet measured in a live run beyond those captures.

- **Menu column.** `DEBUG MENU  ALT+2` is wider than the 200-unit column and runs under the
  viewport; with the console open it is clipped. Likely a `Button` growing to its text, not a layout
  number; the implementer confirms the cause.
- **Header.** `ETHERBOUND` is plain text; the speed and `NEW` buttons are 18-unit mini buttons next
  to a 30-unit clock, so the right edge looks unbalanced; a blank strip trails `NEW`.
- **Status column.** 296 units wide, but only `CARRY` shows and it is narrower than the column.
  `ACT` appears only while an activity runs. The rest is empty background.
- **Font.** The HUD uses Inter. `STYLEGUIDE.md` [Sec. 2] specifies JetBrains Mono for interface and
  records the font as open work.
- **Feed.** One line at a time, no time stamp, no category rule in the footer slot; the 8-row cap
  is invisible because the 80-unit slot shows one or two rows.
- **Console.** `DevConsole` extends below the viewport rectangle and covers the footer (feed row
  visible through it in `dev-console.png`).
- **Build panel.** Text-only slots in a 360-unit drawer that covers a third of the world; no
  material swatch, no empty-state wording beyond the disabled slot.
- **Surfaces.** Panels are flat fills with a 1-unit border; the viewport has no frame, and none of
  the always-on scanline treatment of `STYLEGUIDE.md` [Sec. 15] exists.
- **Data on hand.** `WorldFrame` carries the clock, every actor (name, kind, position, height,
  activity with `started_minute`/`ends_minute`) and `LoadKg`; `HostMenuPayload` entries carry
  `action`, `available`, `reason`, `subject`. The sim exposes no HP, EP or needs.

## 2. Decisions

Status after review: D2, D3, D5, D6 and D8 were answered by the user; D4 was not answered, so the
recommended option is assumed and flagged below.

- **D1. The grid does not move (settled).** The design frame in `HudLayout` stays 2560x1440, so
  the existing `HudLayoutTests.cs` assertions stay valid. Polish happens inside each slot; the only
  layout change is how the frame fits a window that is not exactly 16:9 (D8).
- **D2. Figma is ignored (decided).** No Figma frames, export or comparison in this plan. Code
  follows the tokens in `STYLEGUIDE.md` [Sec. 3]. The two Figma items already in `PENDING.md`
  (Dev-004 comparison and export) stay parked and untouched.
- **D3. Font.** Add JetBrains Mono (OFL) under `game/assets/fonts/` for HUD text, keeping Inter only
  as fallback for glyphs it lacks. **Approved**; ship the OFL licence file next to the font.
- **D4. Feed placement (assumed, not answered).** Keep the footer slot and make it a three-row
  log with time stamps and category rules, mouse-wheel history up to 100 rows. The alternative
  (floating over the viewport's bottom-left, `STYLEGUIDE.md` [Sec. 5]) is not planned; the user can
  still ask for it before Stage 4.
- **D5. `NEARBY` panel.** A list of actors Niko can currently see, to fill the status column. It
  reads `WorldFrame.Actors` filtered to those whose position projects inside `GameViewport`, so it
  never lists what Niko cannot see ("reactions come from knowledge", `AGENTS.md`). Recommended:
  **Approved.**
- **D6. Load bar.** A `LOAD` meter needs a maximum the sim does not expose (10 kg is the free
  threshold, 40 kg the single-object lift limit). Recommended: a two-zone bar, green to 10 kg and
  yellow beyond, scaled to 40 kg, with the number always shown. **Approved.**
- **D7. Effects budget (settled).** Only the effects `STYLEGUIDE.md` [Sec. 15] already allows:
  subtle scanlines on panels and `glitch-in` on a new feed row. No full-screen effect, no effect
  over the 3D view. A single `HudTheme.Motion` switch turns all motion off.
- **D8. Target window: 2K, maximized (decided).** The user's monitor is 2560x1440 and the game
  runs maximized there. `game/project.godot` `window/size/viewport_width/height` go from 1280x720
  to 2560x1440 (the restore size); `WorldClient` already maximizes unless `--shots` is set. The
  HUD still scales by the window, but a maximized window is not exactly 2560x1440: the title bar
  and taskbar take height, so it is wider than 16:9 (roughly 2560x1370). `HudLayout.Solve` scales
  by height only, which would leave the frame short of the right edge. Change it to scale by
  `min(width / 2560, height / 1440)` and centre the frame, so any window shows the whole HUD with no
  overflow. 1280x720 stays the minimum supported window (`STYLEGUIDE.md` [Sec. 16]).

## 3. Scope

### 3.1 Stage 1: foundations (`game.ui`)

- `HudTheme`: load the font (D3); add `Accent` helpers (primary, danger, disabled) and a
  `Chip(text)` for hotkeys; add a `Meter(ratio, zones)` pure function that returns cell counts
  (`STYLEGUIDE.md` [Sec. 12]); a `Motion` flag (D7).
- A small panel shader (`game/ui/` `.gdshader`, `CanvasItem`) for the 1-px scanline pattern at the
  alpha of [Sec. 15], applied to the HUD panel frames only.
- Viewport frame: a 2-unit `--line-hi` border and four cyan corner ticks drawn around the
  `GameViewport` rectangle, outside the rendered rectangle so picking and `PixelView` are untouched.
- Menu column: fixed-width buttons with `ClipText`, the label left and the hotkey as a right-aligned
  chip (`GAME` ⟷ `ALT+1`), so no label can exceed 200 units. States: normal, hover (inverted),
  active (cyan rule on the left), disabled.

### 3.2 Stage 2: header

- Brand: `ETHERBOUND` with a cyan `▍` glyph and a dim `// LIVE SIMULATION` subtitle that turns
  `// PAUSED` (yellow) while the clock is paused, from `WorldFrame` only.
- Clock block: `DAY 01 · 00:54` with the existing green/yellow rule, then a segmented speed
  control (`II`, `x1`, `x3`, `x10`) of equal-width cells sized to the 64-unit header, and `NEW` as a
  separate bracket button. Events and wiring are unchanged.
- Remove the empty trailing strip by anchoring the block to the header's right edge.

### 3.3 Stage 3: status column

- `ACT`: title, the action label, a progress bar from `(now - started_minute) / (ends_minute -
  started_minute)` and the remaining minutes; hidden when idle, as today.
- `CARRY`: full column width, one row per slot (`L`, `R`, `BACK`), item name and count, and the
  `LOAD` line with the D6 meter; yellow above 10 kg as today.
- `NEARBY` (D5): up to eight rows, name, kind tag, distance in metres and the activity label, sorted
  by distance; selecting a row does nothing in this plan.
- `STATUS` stays hidden: no HP/EP until the sim exposes vitals (Dev-004 D4).

### 3.4 Stage 4: feed and footer

- Rows with `HH:MM` game time, a 2-unit left rule by category (`seen` cyan, `act` line-hi, `warn`
  yellow, `fail` red, `ether` magenta) and the text; older rows dim to 45 % opacity.
- Three visible rows in the 80-unit slot, mouse-wheel scrolling, 100-row cap (was 8).
- `glitch-in` on a new row (120–340 ms, skipped when `Motion` is off).
- Input line: the green `>` prompt stays; add a dim `ENTER` chip on the right and a focus glow.

### 3.5 Stage 5: menus, tooltips and the build panel

- `ActionMenuOverlay`: hotkey chips, the existing cyan left rule, a soft drop shadow, a 100 ms
  open step; entry order and content are untouched (it renders what the sim returns).
- Tooltip control for an unavailable entry's `reason`, replacing the engine default tooltip.
- `BuildPanel`: a material swatch per slot using the colour of the sprite sheet already mapped for
  that material, the sim's own reason as a second line when disabled, and an empty state
  (`NOTHING BUILDABLE HERE`) when `Menu.Build` returns no entry. The panel height shrinks to its
  content, with the current 360 units as the maximum. The build path (D5 of Dev-004) is unchanged.

### 3.6 Stage 6: console containment

- `DevConsole` is clipped to the `GameViewport` rectangle and its table scrolls inside it, so it can
  never cover the footer. Section sidebar, `Regenerate` and the NPC table keep their data and events.

## 4. What must not break

- The client never simulates: every number comes from `WorldFrame` or a host payload; `sim/` is
  untouched and nothing is written from the HUD. `NEARBY` and `ACT` are reads.
- One action API: menus and the build panel still show exactly the entries the sim returned and
  submit that entry's own action.
- Layout contract: the existing `HudLayoutTests.cs` assertions pass unchanged; the viewport rectangle fed to
  `PixelView.SetTargetRect` does not move, so picking and ray mapping are unaffected.
- Input: `W`, `A`, `S`, `D`, `T`, `C`, `X`, `O`, `H`, `V`, `1`, `2`, `4` and ALT+1/2/3; movement is
  gated only by `CanMoveWorld`, never by a panel being open.
- Existing events: pause, speed, `NEW`, input line, feed, carry, activity, compass, LLM placeholder.
- Colours stay in `HudTheme`; no hex literal outside it. Magenta stays reserved for Ether.
- No schema change, no migration, no goldens change.

## 5.1 Result

Built as planned, with these differences and open points:

- The menu label is `DEBUG`, not `DEBUG MENU`: with a hotkey chip the longer label does not fit
  the fixed 200-unit column.
- The feed panel has no `FEED` title row; three rows need the whole 80-unit slot.
- The radial menu's verb slots show their own digit (`1  WAIT`), since 1–9 already focus them.
- The console overflow was an autowrap `Label` inflating its container, not the form: fixed with
  `ClipText`, a scrolling form and a per-frame re-place (`PITFALLS.md` [Sec. 8]).
- The status column's stack had no anchors, so every panel was narrower than the column; fixed.
- `GameHud` rebuilds its frame when the scale moves, which the plan did not state; the feed
  history is kept in the HUD and replayed.
- Not verified by eye: the `ACT` progress bar (needs a live activity), the disabled-slot tooltip
  and the `--reduce-motion` run. They are in `docs/PENDING.md` with the other manual checks.
- The system map was not updated: no module boundary or data flow changed, only the client computes
  which actors project into the viewport before handing them to the HUD.

## TL;DR

Keep the Dev-004 grid and contracts, target a maximized 2K window and make the HUD feel finished: JetBrains Mono, a fixed menu
column with hotkey chips, a balanced header with a segmented speed control, a status column filled
with `ACT` progress, a full `CARRY` with a load meter and an optional `NEARBY` list, a timestamped
scrollable feed, a tidier build panel and a console that stays inside the viewport. Everything is
read from `WorldFrame` and menu payloads, motion is limited to the effects the style guide already
allows, and `sim/` is not touched.
