# Dev-025: C# simulation and Godot 3D orthographic client

[Architecture] [Migration] [Engine] [Rendering] [Tooling]

EtherBound is singleplayer, and the plan calls for crowds of Extras, richer physics, shaders,
ambient occlusion and a long world. CPython and a WebSocket split between two local processes
serve none of that. This doc ports the game to a deterministic C# simulation and a Godot 4 (.NET)
client in the same process, rendered as real 3D through an orthographic camera with a pixel-art
look. It is a **port, not a redesign**: same rules, events, schema and generators, proven equal
by goldens exported from the Python server. Decided by the user on 25/09/2026.

Reference: `docs/utils/VISION.md` [Sec. 3], [Sec. 4], [Sec. 5], [Sec. 11], [Sec. 14];
`docs/Dev-023.md` [Sec. 0] (kernel findings);
`docs/utils/PITFALLS.md` [Sec. 5]; `CONTEXT.md`.

## 1. Decisions

| Topic | Decision | Why |
|---|---|---|
| Scope | Port only. No new ops, no schema change, no gameplay change until cut-over [Sec. 3.7] | The goldens can only prove equality if nothing else moves |
| Freeze | `server/` and `web/` receive only what the golden export needs. The launcher stays until cut-over | Two moving targets would make parity meaningless |
| Layout | `sim/EtherBound.Sim` (deterministic library), `sim/EtherBound.Host` (thread, real-time pacing, command queue, frames), `sim/EtherBound.Sim.Tests` (xUnit), `sim/EtherBound.Bench`, `game/` (Godot project), `EtherBound.sln` at the root | The sim never sees Godot, and the compiler enforces it |
| Runtime | `net10.0` for every project; Godot 4.7.2 loads it (stage 0) | One runtime, one set of analyzers |
| Godot | 4.7.2-stable, .NET build, `Godot.NET.Sdk/4.7.2`, Forward+ renderer. `GODOT_BIN` points at the editor | SSAO and shadows need Forward+ |
| Threading | The sim runs on one dedicated thread. Godot sends commands (`Input`, `Action`, `Clock`, `NewGame`, and queries such as `Menu`, `Pick`) through a channel and reads an immutable `Frame` (clock, actors, results, activity notices, changed chunk revisions) swapped atomically | "One writer" stays literal, and frame time never depends on tick cost |
| Movement | WASD becomes a `move` command validated by the same op. No prediction. The sim steps movement at `MoveHz` (20, as today); the client interpolates. If stage 3 feels laggy, raise `MoveHz` | Prediction existed to hide network latency, and there is none. It also removes F2's duplicated rules |
| Kernel | Dev-023's F1–F10 are requirements of the port: systems register with an explicit order, handlers are found from `ops.toml` with defaults for unused methods, one result builder, and an architecture test for layering | The port is where they cost nothing |
| RNG | `PyRandom`: a bit-exact port of CPython's MT19937, its integer seeding and the five methods of F4, behind `RngStream` | Worlds and populations must match byte for byte. A faster generator later is a `gen_version` bump |
| Floats | Match CPython where it matters: port its `hypot` (F6). A golden that differs only in the last bit from libm is recorded in `PITFALLS.md` and compared with a tolerance on that field only | Keeps the goldens exact without chasing libm |
| Persistence | `Microsoft.Data.Sqlite`, same schema at `0008_extra`. The engine keeps authoritative state in memory; a session hands out working copies (as SQLAlchemy does) and a commit writes them in one SQLite transaction. The sim's runner adopts a save whose `alembic_version` is `0008_extra`, records its own `schema_version` and leaves `alembic_version` alone until cut-over | The user's save opens in both runtimes during the port; nothing is wiped |
| Data | `ops.toml`, `objects.toml`, `names.toml` and material data are copied to `sim/EtherBound.Sim/Data/` and read with Tomlyn | The Python copies are frozen; the goldens catch any drift |
| Guards | `BannedApiAnalyzers` in `EtherBound.Sim`: `System.Random`, `DateTime.Now`/`UtcNow`, `DateTimeOffset.Now`, `Environment.TickCount*`, `Stopwatch`, `Thread`, `Task.Run`. Warnings are errors. The host may use them | Replaces Ruff `TID251` |
| Camera | Orthographic, yaw 45°, pitch 30°, which gives an exact 2:1 diamond. The render root is scaled vertically by √(2/3) ≈ 0.8165, so 0.5 m = 16 px as in VISION (kept in stage 0) | Keeps today's proportions, so BitCanvas sheets fit |
| Pixels | The world renders into a SubViewport where 1 px = 1 art pixel at x1, scaled x1/x2/x4 with nearest filtering. The camera snaps to the art-pixel grid in projected space, and the remainder offsets the scaled image | Smooth scrolling without shimmer |
| Texturing | Iso-space shader: a top face samples today's iso sheet at its world position projected into sheet space, so one texel lands on one art pixel. Side faces reuse the side sheets and the shear rule. Chosen in stage 0: world-aligned square texels smear diagonally at x2/x4 | Keeps BitCanvas's exact pixel look on 3D geometry |
| Light | One directional sun plus ambient light, shadows on, SSAO on. Stage 0 start: linear ambient 0.25, sun energy 0.8617 toward (x 0.174, up 0.870, y 0.461); tops keep the sheet colour, S and E faces measure within 4/255 of 0.82 and 0.66 | Depth cues from the renderer instead of Dev-024's baked tints |
| Cutaway | The `VISION.md` [Sec. 5] rules stay the spec. Per-level mesh visibility plus a clip-height uniform. Occluders come from a ray from Niko's body toward the camera over the sim grid. The silhouette is a second pass drawn where depth fails | The depth buffer replaces F3's probes and masks |
| Picking | A ray from the cursor through the sim grid (tops, faces, objects, actors, wall edges), run on the sim thread as a query | It must agree with the sim's geometry, not with meshes |
| Actors | Stage 3: capsules; above a threshold, Extras draw through `MultiMesh` | Crowds without one node per Extra |
| Objects | Stage 3: boxes sized from the kind. Stage 5: meshes built from BitCanvas primitive specs (box, cone, cylinder, ellipsoid), with facings by rotation | A spec is already 3D; four facings come free |
| UI | Godot `Control` with a `Theme` carrying the `STYLEGUIDE.md` tokens; same panels, tabs and menus. No text is drawn in the 3D world | Same screen, new toolkit |
| Paths | Art moves to `game/assets/` at cut-over; BitCanvas "Send to game" is retargeted | Godot imports only under `res://` |
| Open docs | Dev-014, 016, 021, 023 and 024 stay in `docs/` untouched and frozen during the port, and are deprecated at cut-over [Sec. 3.7]. An idea that still stands gets a new Dev written against `sim/` and `game/` | Nothing is decided twice. Their references stay valid while the port reads them (Dev-023 [Sec. 0], the Dev-016 menu tiles) |

## 2. Out of scope

- New gameplay, ops or schema; LLM and Jev (their C# runtime is an open question in `PENDING.md`).
- Physics beyond Dev-013's model. Richer physics is a later Dev on the C# sim, never on Godot's
  physics engine (`VISION.md` [Sec. 5]).
- Networking, Linux/macOS builds, modding, outline shaders and post effects beyond SSAO.

## 3. Stages

Each stage ends with `npm run check` green and a commit. A stage does not start while an earlier
one fails.

### 3.1 Stage 0: look spike (go or no-go)

- `server/scripts/export_world.py` (tooling) dumps the seed-7 `test` world and the `lab` world to JSON.
- A `game/` spike loads a dump and draws: terraces, a cliff, the road, the building with its
  doorway, window, slab and roof, and a chest as a box. It uses the camera, pixel and light
  decisions [Sec. 1], iso-space against world-aligned texturing, roof cutaway and the silhouette.
- Measure frame time with all 64 chunks loaded, and shimmer while scrolling at x1/x2/x4.
- Result (GTX 1650, 1280×720, 64 chunks, shadows and SSAO on): frame 5.3/3.1/2.8 ms average at
  x1/x2/x4. Scrolling by whole and fractional art pixels leaves at most 0.003 % of pixels different.
- Deliverable: x1/x2/x4 screenshots for the user, and this doc updated with the TFM, the Godot
  version, the texturing choice and the vertical scale.

### 3.2 Stage 1: solution, guards and goldens

- `EtherBound.sln`, the four `sim/` projects, the analyzers and an architecture test.
- `npm run check` gains `check:sim` (`dotnet test`) and `check:game` (`dotnet build game`, plus a
  Godot headless import when `GODOT_BIN` is set).
- `server/scripts/export_goldens.py` writes `sim/EtherBound.Sim.Tests/Goldens/`:
  - worlds: `test` and `lab` × seeds 0, 7 and 1895070486, with the SHA-256 of every chunk and
    level blob, the objects and the spawn;
  - populations;
  - RNG: the first 1,000 draws of each F4 method per stream;
  - scenarios: scripted submits (walk, stairs, dig, take/put/drop, push, throw, hit and break a
    wall, climb, wait over ticks, Extras over 120 ticks at x1 and x10), each a step list (`place`,
    `spawn`, `wall`, `submit`, `tick`, `brain`, `clock`) the C# tests replay, with every result,
    the logged events and the final state (actors, objects, wall integrity, one blob SHA-256);
  - menus: the Dev-016 tiles and the lab bays; `world-parity.json` is reused as is.
- Running the export twice gives identical files; `check:goldens` re-exports and fails on a diff.

### 3.3 Stage 2: port the simulation

- Order: `rng` → `world` (materials, catalog, chunk, grid, A*, noise, `test`/`lab`, population) →
  `events` → `db` (schema, load/save, runner) → `engine` (submit pipeline, handlers, physics, menu,
  setup, activities) → `clock` → `minds` (`ExtrasBrain`) → `host`.
- Ported unit tests are named by feature, plus the golden tests [Sec. 6].
- `EtherBound.Bench` on the `lab` map with 1,000, 5,000 and 10,000 Extras: milliseconds per
  game-minute tick at x10 and per movement step. The numbers go into `CONTEXT.md`.
- Initial result (Release, 8 logical cores): 298 / 1,408 / 3,434 ms average per tick at x10 for
  1,000 / 5,000 / 10,000 Extras. It missed [Sec. 6] 8 (1,000 Extras within 100 ms) by about 3×.
- Perf pass: carried payloads are cached until an inventory-changing op; standing-surface and step
  queries are cached by grid revision; accepted wander paths are reused only on the same grid
  revision; diagonal checks avoid temporary sets; A* skips stale frontier entries and reuses its
  search workspace; and `EventBus` reuses its handler snapshot until subscriptions change. Minds
  read the tick snapshot through `GetTickState`; SQLite writes from one tick share an outer
  transaction while each engine publish retains a savepoint.
- Result after the pass (Release, .NET 10.0.12, 8 logical cores; 5 warmup and 100 measured ticks):
  64.864 / 372.898 / 880.881 ms average per tick at x10 and 108.090 / 531.689 / 1,269.047 ms
  p95 for 1,000 / 5,000 / 10,000 Extras; a single player move step averages 0.147 / 0.108 / 0.141
  ms. Acceptance is the average for 1,000 Extras; the 100 ms gate passes. The p95 is recorded as
  diagnostic data and remains slightly above 100 ms for that population.
- `EtherBound.Host` is still a skeleton and the sim is invoked synchronously; wire it into Godot in
  Stage 3. The larger populations remain useful scaling measurements, not Stage 2 gates.

### 3.4 Stage 3: the world on screen

- The host is wired into Godot. Chunk meshing uses one mesh per chunk and `z` band, with only
  exposed faces: ground tops and faces, floors, 0.5 m slabs, 1/4 m walls with doorway and window
  openings, and VOID excavation. Chunks stream at radius 2 by revision.
- Stage 0 materials; capsules for actors; WASD; camera follow; zoom; clock, speed and pause HUD.

### 3.5 Stage 4: interaction and UI

- Picking; the right-click list and the `V` radial menu, both rendering the payload as is.
- `CARRY`, `FEED`, `ACT` and the input line; the `NEW` popover; the `GAME`/`DEBUG`/`LLM` tabs in
  the Dev-019 frame, with the `MAP` form built from `GeneratorSpec` fields.
- Trajectory animation, activity notices, cutaway, silhouette and front-wall stubs.

### 3.6 Stage 5: 3D objects and light

- BitCanvas exports furniture primitive specs from `furnitureData.js` as JSON into
  `game/assets/furniture/`; Godot builds the meshes with BitCanvas palettes and ramps.
- Tune the sun, shadows and SSAO at x1/x2/x4.

### 3.7 Stage 6: cut-over

- Parity walk [Sec. 6] 7. A Windows export runs from a clean folder, with saves in `user://`.
- Delete `server/`, `web/`, `launcher/`, `EtherBound.exe`, `server/pyproject.toml`,

  `game/assets/sprites/`.
- Docs: rewrite `CONTEXT.md`; rewrite `PITFALLS.md` [Sec. 1], [Sec. 3], [Sec. 5] and [Sec. 7];

## 5. What must not break

- `VISION.md` [Sec. 14], word for word: the sim thread is the only writer, and the client only
  sends commands.
- Same seed, same world bytes, population and event log as the Python server.
- The user's `data/etherbound.db` opens in the C# sim with no migration, and still opens in Python
  until cut-over.
- Menus are built by the sim; the client never adds, removes or reorders an entry.
- No Python or web feature work during the port.

## TL;DR

- Singleplayer: the Python server and the Phaser client become one process, with a deterministic
  C# sim on its own thread and a Godot 4 .NET client that only draws and sends commands.
- 3D orthographic camera (yaw 45°, pitch 30°, exact 2:1), low-res buffer with integer scaling,
  BitCanvas sheets through an iso-space shader, SSAO and shadows from the renderer.
- Port, not redesign: goldens from Python (worlds, RNG, scenarios, menus) must match exactly;
  `PyRandom` reproduces CPython's MT19937; the same SQLite save opens in both runtimes.
- Seven stages, from a look spike (go or no-go) to cut-over. The open Devs (014, 016, 021, 023,
  024) stay frozen and are deprecated at cut-over; surviving ideas get new Devs.
