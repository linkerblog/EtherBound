# Dev-009: BitCanvas as the in-repo texture generator (Tooling)

[Tooling] [Art pipeline] [Docs] [Refactor]

The user moved BitCanvas into the repository (commit `v0.6.3`, `BitCanvas/`) because it becomes
the main tool for generating textures. Today it lives there as a foreign body: it is not a
module in `docs/utils/VERSION.md`, `CONTEXT.md` does not mention it, its UI, comments and toasts
are Spanish (AGENTS.md: English only), it still calls itself "Pixelcanvas", and its exports use
names that must be renamed and copied by hand into `src/sprites/`. This doc makes it a
first-class module that writes its sheets straight into `src/sprites/`, without changing a
single generated pixel.

Reference: `AGENTS.md` (Conventions: English only, Versions, Notion); `docs/utils/VISION.md`
[Sec. 3]; `CONTEXT.md` (web.game, "Side sheets are unsheared", "Assets outside `web/` must be
static imports"); `docs/done/Dev-008.md`, `docs/done/Fix09.md` (sheet formats).

## 1. Current state (measured 23/09/2026)

| File | Size | What it is |
|---|---|---|
| `BitCanvas/index.html` | 149 lines | Page shell, `lang="es"`, plain `<script defer>` (no modules, no build) |
| `BitCanvas/app.js` | 1642 lines | Terrain generator (grass, planks, cobblestone, concrete), voxel furniture, preview, exports |
| `BitCanvas/pixelart.js` | 833 lines | Ray-traced "pixel" furniture style; comments in Spanish |
| `BitCanvas/pixelcanvas.css` | 123 lines | Tool-specific styles |
| `BitCanvas/styles.css` | 9 lines | Base styles, imports Google Fonts |

- Opens directly from disk (`file://`); it has no dependencies and no build step.
- Game sheet formats already match: the "variants" atlas is 4 × 64×32 = 256×32 (same as
  `src/sprites/*/*_x4.png`) and the side sheet is 128×32, cap row over fill row, unsheared
  (same as `*_side_x4.png`, see CONTEXT "Side sheets are unsheared").
- Spanish text: 71 accented lines in `app.js`, 24 in `index.html`, 24 in `pixelart.js`, plus
  unaccented Spanish strings and comments.
- `Math.random` is used only for the "random seed" and "random palette" buttons (UI, not
  generation). The generation itself is seeded.

## 2. Decisions to approve

| Topic | Decision | Why |
|---|---|---|
| Location | Stays at `BitCanvas/` in the root | The user placed it there; moving it buys nothing and breaks their muscle memory |
| Name | "BitCanvas" everywhere: title, brand, breadcrumb, aria labels, export prefix; one stylesheet `bitcanvas.css` replaces `styles.css` and `pixelcanvas.css` | One name for one tool |
| Module | New `bitcanvas` module, path `BitCanvas/`, registered at `v0.0.0` and bumped to `v0.0.1` by this change | AGENTS.md: every module is listed and versioned |
| Language | Every UI string, toast, `aria-label`, `title`, `meta` and comment translated to English; `lang="en"` | AGENTS.md: English only, never two languages in one file |
| Look | BitCanvas is redesigned to `docs/utils/STYLEGUIDE.md`: its palette, font, square corners, bracket and `.mini` buttons, `h3` panel headers, tabs, list rows, feed items and status pills. Its menu is reorganized into three panels and an export bar [Sec. 3.5] | The user asked for it: one visual language across the project. Today BitCanvas is a light, rounded, serif landing page with a single long sidebar that mixes the material list and the generator controls |
| Style guide scope | STYLEGUIDE gains one line saying BitCanvas follows it, except [Sec. 1] (layers over the world) and [Sec. 15] (diegetic effects), which only make sense in the game | Glitch and CRT effects are events that happen to Niko; a texture tool has none |
| Game-ready exports | The two exports the game consumes are named exactly like the game's files [Sec. 3.3] | Today every export is renamed by hand; a wrong name silently leaves the old sheet in place |
| Send to game | A "Send to game" button writes both sheets of the current material directly into `src/sprites/<folder>/`, through the browser's File System Access API on a folder the user picks once [Sec. 3.4] | The user asked to stop copying files by hand. The API needs no server, so BitCanvas still opens from disk. Rejected: an endpoint in the game server (a dev tool writing through the game's backend mixes concerns and needs the server running) and a separate Node helper (one more process to start) |
| Overwrite | Sending overwrites existing sheets without a confirmation dialog | Every sheet in `src/sprites/` is committed, so `git restore` is the undo; a dialog on every send is the friction the user wants gone |
| Launching | Root script `npm run bitcanvas` opens `BitCanvas/index.html` in the default browser. No launcher key | One line, no C# change. A launcher key can come later if the tool is used daily |
| Output | Pixel-identical to today for the same inputs | This is housekeeping, not a generator change; [Sec. 5] proves it |
| Vision | `docs/utils/VISION.md` [Sec. 3] names BitCanvas as the source of terrain and furniture art [Sec. 3.7] | Art pipeline is a fixed decision; the vision must say where art comes from |

## 3. What changes

### 3.1 Rename and translate (`bitcanvas`)

- `index.html`: `lang="en"`; title `BitCanvas — Textures and furniture`; `meta description`,
  brand (`bit<span>canvas</span>`), breadcrumb `BITCANVAS`, every visible label, `small`
  caption, `aria-label` and `title` in English. The markup itself is rebuilt in [Sec. 3.5].
- `app.js`: every toast, readout and spec string in English; palette `detail` strings
  (e.g. `'Roble cálido'` → `'Warm oak'`); comments in English.
- `pixelart.js`: every comment in English (section headers such as `// --- Mobiliario pixel art`
  → `// --- Pixel art furniture`). No identifier changes; they are already ASCII English.
- Keep all `data-*` values, `state` keys and material keys as they are. Element `id`s and the
  classes `app.js` queries are kept wherever [Sec. 3.5] still has the element; see the hook list
  there.

### 3.2 No generation changes

Do not touch palettes' ramps, constants, noise, hashes, seeds, draw order, export canvas sizes or
`drawPreview`'s drawing. The translation of a palette `name`/`detail` must not change which ramp
is selected. The redesign [Sec. 3.5] is markup, CSS and UI wiring only.

### 3.3 Export names

Game-ready exports get the game's file names so they can be dropped into `src/sprites/`
unchanged. The status line names the destination folder.

| BitCanvas material | Variants atlas (256×32) | Side sheet (128×32) | Folder |
|---|---|---|---|
| `grass` | `grass_x4.png` | `grass_side_x4.png` | `src/sprites/grass/` |
| `planks` | `planks_x4.png` | `planks_side_x4.png` | `src/sprites/floor/` |
| `cobblestone` | `stone_x4.png` | `stone_side_x4.png` | `src/sprites/floor/` |
| `concrete` | `concrete_x4.png` | `concrete_side_x4.png` | `src/sprites/floor/` |

- Keep the mapping as one table at the top of `app.js` (`GAME_SHEETS`), not scattered strings.
- `cobblestone` → `stone`: the user confirmed on 23/09/2026 that `floor/stone_x4.png` came from
  BitCanvas's cobblestone. `concrete_*` files are new and nothing imports them yet (wiring them
  into `terrainSprites.ts` is not part of this doc).
- Exports the game does not consume keep a tool-prefixed, seeded name, with `pixelcanvas-`
  → `bitcanvas-`: single top `bitcanvas-<material>-top-64x32-<seed>.png`, side pairs
  `bitcanvas-<material>-sides-256x16-<seed>.png`, furniture
  `bitcanvas-furniture-<piece>-<style>-<w>x<h>-<seed>.png`.

### 3.4 Send to game (`bitcanvas`)

A new module file `BitCanvas/gamesync.js`, loaded with `<script defer>` before `app.js`, owns
the folder handle and the writes. `app.js` only calls it.

- **Button.** "Send to game" in the export panel, shown for the four terrain materials, hidden
  for furniture. One click writes the variants atlas and the side sheet of the current
  material, using the [Sec. 3.3] names, into `<sprites>/<folder>/`, the folder created if
  missing (`getDirectoryHandle(name, { create: true })`). Encode through `canvas.toBlob` with
  `image/png`, exactly like the download path, so the bytes are identical.
- **Picking the folder.** The first send calls `showDirectoryPicker({ mode: 'readwrite',
  id: 'bitcanvas-sprites' })`. The user picks `src/sprites/`. Accept it only if it is named
  `sprites` and already contains a `grass` or `floor` subfolder; otherwise refuse with a status line
  ("Pick EtherBound's src/sprites folder") and write nothing. This guards against writing into
  a random folder.
- **Remembering it.** Store the handle in IndexedDB (database `bitcanvas`, store `handles`,
  key `sprites`). On later sends, call `queryPermission({ mode: 'readwrite' })` and, if it is not
  `granted`, `requestPermission` inside the click handler (it needs the user gesture). Chromium
  asks once per session. If storing the handle fails, fall back to picking every session.
- **Changing it.** A small "Change folder" link next to the button clears the stored handle and
  opens the picker again. Show the current folder name (`handle.name`) beside it.
- **Feedback.** On success, a status line names both files, e.g. "Sent grass_x4.png and
  grass_side_x4.png to sprites/grass/". On any error (permission denied, disk error, picker
  cancelled), a status line with the reason. Encode both PNGs before writing either, so an encoding
  failure writes nothing; if a write fails, the status line names the file that did not land.
- **Unsupported browser.** If `window.showDirectoryPicker` is missing (Firefox, Safari), hide
  the button and keep the downloads. The user's browser is Chromium-based (`docs/done/Fix04.md`
  uses Chromium DevTools).
- **The running game.** The sheets are static imports in `web/src/game/terrainSheets.ts`, so
  Vite should reload the game when a sheet changes. Acceptance [Sec. 5] checks it; if Vite does
  not pick the change up, a manual reload is acceptable and CONTEXT records it as a pitfall.
- The download buttons stay as they are.

### 3.5 Redesign to the style guide (`bitcanvas`)

`index.html` is rebuilt and `bitcanvas.css` written from scratch; `styles.css` and
`pixelcanvas.css` are deleted. Every rule below cites `docs/utils/STYLEGUIDE.md`.

**Layout.** Desktop only, minimum 1280×720, no page scroll and no phone layout [Sec. 16]; the
current `@media` breakpoints go. The side panels scroll inside themselves.

- **Top bar.** Brand and module version, breadcrumb (`#breadcrumb-material`), status pills
  [Sec. 13] for projection, tile size and current seed, and the help `?` as a `.mini`.
- **Left panel `MATERIALS`.** Tabs [Sec. 14] `TERRAIN` and `FURNITURE` replace the three
  category headings. Each material is a list row [Sec. 14]: glyph and name, and a `.meta` line
  with its game file for terrain (`grass/grass_x4`) or its category for furniture (`Storage`).
  The selected row takes the `--cyan` left border. The "add material" button goes (it only
  showed a "coming soon" toast).
- **Centre.** View switch `TILES`/`BLOCK`/`SIDES` as `.mini` buttons with the `.active` style
  [Sec. 6], hidden for furniture (it always shows the block). The preview canvas sits on an 8 px
  checkerboard of `--panel` and `--bar`, so transparency reads, with no filter, shadow, border
  radius or overlay on the canvas [Sec. 1]: the pixel art stays untouched. The canvas keeps its
  768×768 backing store (4 backing px per art pixel) and is displayed at 192 × n CSS px, with n
  the largest of 4, 3, 2 that fits, so each art pixel is exactly n screen pixels [Sec. 4:
  integer steps only]. A mode caption line (`#stage-mode`, `#stage-dimensions`) sits under it.
- **Right panel `GENERATOR`.** `h3` panel headers [Sec. 5] (solid `--panel`, not translucent:
  nothing lies behind them) in this order: `STYLE` (furniture only), `PALETTE`, `SEED`,
  `SURFACE` (density, brightness, dirt or ground shadow), `FORMAT` (the read-only tile, variant
  and face spec). Palette rows show swatches computed from the ramps in `app.js` instead of the
  hardcoded CSS colours, so they cannot drift. `RANDOM` and `↻` are `.mini`. Sliders are flat:
  `--line-hi` track, `--cyan` fill, square thumb, mono readout. Toggles stay checkboxes, drawn by
  CSS as `[x]`/`[ ]` in mono (`:checked` on the hidden input), so their listeners do not change.
- **Bottom export bar.** `[ SEND TO GAME ]` is the only `button.primary` [Sec. 7], with the
  destination path beside it, the folder name and `CHANGE` (`.mini`); hidden for furniture and
  unsupported browsers [Sec. 3.4]. The four downloads are `.mini`. On the right, a status feed
  replaces the toast.
- **Status feed.** The last three messages as feed items [Sec. 11]: `.act` for a done action,
  `.warn` for a refusal, `.fail` for an error. The words carry the meaning (`SENT`, `SAVED`,
  `CAN'T SEND`, `FAILED`), never only the colour [Sec. 16]. `showToast(message)` becomes
  `showStatus(message, kind)`; `#toast` stays as the feed's id with `role="status"`.
- **Help.** `?` opens a popover anchored to it (not centred) with the hotkeys and the formats;
  Esc closes it.

**Tokens.** `bitcanvas.css` copies the `:root` palette of [Sec. 3] and the reset of [Sec. 4]

**Keyboard** [Sec. 16]. Ignored while a text field has focus [Sec. 9]:

**DOM hooks.** `app.js` looks elements up by id and class. The rebuilt markup keeps these,

`#stage-mode`, `#stage-dimensions`, `#breadcrumb-material`, `#generator-title`,

## 4. What must not break

- The game: this change commits no new sheet; `src/sprites/` files, `terrainSprites.ts` and
  `terrainSheets.ts` end untouched (any test send is restored); web build and tests pass.
- BitCanvas output for the same material, palette, seed, density, brightness and dirt setting

## 5. Acceptance

1. Before any edit, export from BitCanvas with the defaults (grass, meadow, seed `A17F3C`,
   density 6, brightness 58): variants atlas and side sheet. Repeat for planks, cobblestone and
   concrete (seed `A17F3C`, first palette). Keep the eight PNGs aside.
2. After the change, repeat step 1. Every new file's SHA-256 equals its counterpart's
   (`certutil -hashfile <file> SHA256`); only the names differ, as in [Sec. 3.3].
3. `grep -nP "[áéíóúñ¿¡]" BitCanvas/*` finds nothing; a read of `index.html`, `app.js` and
   `pixelart.js` finds no Spanish words left.
4. `grep -rin pixelcanvas BitCanvas/` finds nothing.
5. `npm run bitcanvas` opens the tool; every control, both tabs, the three views and the
   furniture pieces work as before.
6. **Style.** `bitcanvas.css` has no `border-radius` other than the reset's `0`, no colour
   outside the STYLEGUIDE [Sec. 3] tokens (swatches and the preview excepted), no magenta and no
   font but JetBrains Mono. At 1280×720 the page does not scroll, and the preview shows each
   art pixel as a whole number of screen pixels (zoom a screenshot: no uneven pixel widths).
   Every hotkey in [Sec. 3.5] works and is ignored while typing in the seed field. Refusals and
   errors appear in the status feed with their word (`CAN'T SEND`, `FAILED`).
7. **Send to game, scratch folder.** Create `%TEMP%\bitcanvas-test\sprites\grass\`. Send each of
   the four materials, picking that `sprites` folder. `grass/` and `floor/` hold the eight
   [Sec. 3.3] files (`floor/` created on the fly), each byte-identical to its download from step 2.
8. **Guards.** Picking a folder not named `sprites`, or one without `grass`/`floor`, writes
   nothing and shows the refusal in the status feed. Cancelling the picker shows a status line and writes nothing.
   With furniture selected the button is hidden.
9. **Remembered folder.** Close and reopen BitCanvas; the next send asks only for permission,
   not for the folder. "Change folder" opens the picker again.
10. **Real send.** With the game running (`EtherBound.exe`), send grass with a different seed
   into the real `src/sprites/`. The game shows the new grass after Vite reloads, or after a
   manual reload (record which in CONTEXT). Then `git restore src/sprites` and confirm
   `git status` is clean there.
11. `cd web && npm test && npm run build` passes.

## TL;DR

BitCanvas becomes a proper module (`bitcanvas`, v0.0.1) without changing a generated pixel:
renamed from Pixelcanvas, fully translated to English, redesigned to STYLEGUIDE (dark mono
terminal look; materials, preview and generator in three panels over an export bar with a
status feed and hotkeys), game-ready exports named like the files in `src/sprites/`
(`cobblestone` → `stone`, confirmed), and a "Send to game" button that writes
both sheets straight into `src/sprites/<folder>/` through the File System Access API (pick the
folder once, no server, git is the undo). `npm run bitcanvas` opens it; VISION, VERSION,
CONTEXT and Notion name it as the source of terrain and furniture art. Byte-identical files
before and after, and between send and download, prove nothing moved. Recipes, new materials
and furniture sending are deferred.
