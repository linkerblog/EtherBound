# Dev-036: Construction system, phase 1 (walls and floors)

[Feature] [World] [Engine] [Persistence] [Architecture]

Give Niko, and later NPCs, a way to put a wall on a tile edge and a floor on a tile through the
existing op catalog. The geometry is designed in full now (6 slots per tile, canonical north and
west edges) and shipped in three phases; this doc lands phase 1 and the data model the later
phases need, so the schema does not have to move again.

Reference: `docs/utils/VISION.md` [Sec. 5] (walls occupy tile edges, doorways are edge openings),
[Sec. 6] (mutable 3D space), [Sec. 7] (an op without a handler is never offered, menus are
generated); `docs/done/Dev-007.md` (op vocabulary, activities); `docs/done/Dev-021.md` (wall lines
and heights, the idea that survived the cut-over as this doc); `docs/PENDING.md` (the `build` op
that needed its own gameplay doc); `CONTEXT.md` (Contracts, Ops, Data model).

## 1. Decisions

| Topic | Decision | Why |
|---|---|---|
| Op name | Implement the catalog's `build`; no `build_wall` | The vocabulary is data and `build` is already declared with the right targets. A second key would be two verbs for one behaviour |
| Demolition | Stays `break` | It already resolves energy against a wall edge and opens it at zero integrity (F7) |
| Slots | 6 per tile: `N`, `W` (edges) and `H`, `V`, `D1`, `D2` (interior) | The two edge slots are already what the world stores (F2); the four interior ones are the new part and the whole reason the schema is designed now |
| Canonical edge | A tile owns only `N` and `W`; `south` becomes `north` of `y+1`, `east` becomes `west` of `x+1` | `Edges.Canonical` already does this for physics, so the rule exists once and both ops share it. Any "south/east of X" request converts before validating, so a wall is never stored twice |
| Storage | `chunk_level` gains `slot_mask` (uint8 x 1024, NULL = all zeros, like `dug`) and `slot_mat` (uint16 x 1024) for the interior slots; the edges stay in `wall_n`/`wall_w` | Walls already travel to the client as chunk blobs indexed per cell, and `wall_integrity` shows how sparse damage is done. A `walls(x, y, z, slot, material, hp)` table would need a second payload and a join on every `CanStep` |
| Bitmask | `N=1`, `W=2`, `H=4`, `V=8`, `D1=16`, `D2=32` | One byte per cell is the cache key for the region graph in [Sec. 4] |
| Migration | Build the runner: `0009_walls` applied stepwise on top of `0008_extra` | F3. A new file alone would make every existing save unopenable. `EnsureSchema` applies the pending steps in order from the save's own `alembic_version` and then writes the head |
| Integrity | `wall_integrity` is rebuilt as `wall_slot`, keyed by `(cx, cy, z, cell_index, slot)` | One row namespace for edge and interior slots; a wall edge keeps its current rows, the interior ones start empty |
| Cost | `build_cost` in `materials.toml`, symmetric with `dig_cost` | Data, not code: a new material is a new row, not a new branch (F6) |
| Duration | `build` is an activity: `ceil(30 x build_cost x length / tool)` min, with the best held `tool.build` and a bare-hand factor of `0.25` | `dig` is the model (`DigOp` in `Engine/Ops/BodyOps.cs`). Making it durative is what gives interruption and progress for free |
| A* invalidation | Grid-wide `InvalidateNavigation()` in phase 1 | A build is rare and human-initiated, the two caches are cheap to rebuild and `ExtrasBrain` already replans on the revision. Per-chunk invalidation is a measured change and goes to [Sec. 10] |
| Building on an actor | Refused | The body stands where the wall would be, and displacing it is a movement decision, not a build one |
| Phasing | Edges, then halves, then diagonals | Halves are the hard part: they split one tile into regions the pathfinder has to know about |

## 2. Geometry

Each 1 m tile has 8 possible lines, all through an edge or the centre:

```
   NW ─────── N ─────── NE
    │ ╲       │       ╱ │
    │   ╲     │     ╱   │
   W ─────── C ─────── E      W-E = half horizontal (H)
    │   ╱     │     ╲   │      N-S = half vertical (V)
    │ ╱       │       ╲ │      NW-SE = diagonal D1
   SW ─────── S ─────── SE     NE-SW = diagonal D2
```

The 8 lines divide the tile into 8 triangular sectors. `H` and `V` are 1 m, the diagonals
1.41 m, so a build cost that ignores length would make a diagonal wall cheap; the length is a
factor from [Sec. 1] and no more.

A wall is a segment with a nominal 10-20 cm thickness, not a plane, so nobody squeezes through a
join, above all the X in the centre where two diagonals cross.

## 3. Data model

Migration `0009_walls`, applied by the runner of [Sec. 1] and embedded like `Schema0008.sql`:

- `ALTER TABLE chunk_level ADD COLUMN slot_mask BLOB` and `ADD COLUMN slot_mat BLOB`, both
  nullable, NULL meaning all zeros, so a `0008` chunk blob keeps loading unchanged.
- `wall_integrity` is copied into `wall_slot` `(cx, cy, z, cell_index, slot, joules)`, with
  `slot` holding the same letters as the bitmask, and the old table is dropped.
- `alembic_version` moves to `0009_walls` and `world_meta.schema_version` to `sim-0009`.

Walls carry no `hp` column: integrity is joules in the sparse table, as it is today for objects
and for edges. The source design's `walls(x, y, z, slot, material, hp)` table is the rejected
alternative, for the storage reason in [Sec. 1].

## 4. Pathfinding

Phase 1 changes nothing: a tile without interior slots is one A* node, as today (F5). A wall on an
edge only blocks the transition between two tiles, which `CanStep` already reads.

From phase 2, `H` or `V` can split a tile into regions that do not connect to each other, and the
node becomes `(Spot, region)`. Per tile, the connected components over the 8 sectors are computed
from the cell's `slot_mask`, cached by that byte and recomputed only when it changes. Example: in
`(2, 1)` with `D1`, region 1 (the NE triangle) touches the north and east edges and region 2 (the
SW triangle) touches the west and south; a step from `(2, 0)` enters region 1 and one from
`(1, 1)` enters region 2.

## 5. Phase 1 cut

1. Place and remove a wall on an edge, and a floor on a tile, with material and cost.
2. `validate` respects reach and headroom (`h+1..h+3` clear) and refuses to build over an actor.
3. A completed build writes the wall, emits its event and commits both in one transaction.
4. `Menu` and `Pick` address a bare edge, so a wall can be built where there is none (F4).
5. A* drops its standing and step caches once, through the existing revision (F5).
6. The client remeshes only the dirty chunk and its neighbours, as `dig` does today.

## 6. What must not break

- One action API: `build` goes through `Submit` like every other op, with a generated menu entry
  and no client-side shortcut.
- The client never simulates. It draws the wall the sim committed and remeshes the dirty chunk.
- The generated `test` and `lab` worlds keep their bytes (`WorldGenerationGoldens.cs`); this doc
  adds no generator output.
- The catalog keeps its 58 keys and the same targets; `build` gains a handler, not a new key.
- A `0008` save opens, is upgraded to `0009` in place and reopens with its walls, objects and log
  intact (`SaveCompatibility.cs`).
- The cutaway still cuts a front wall to a stub, and a built wall is still cut with terrain.
- Replay: every build decision is a logged event with its seed, like every other op.

## 7. Acceptance

### Automated

Two deviations from [Sec. 1]/[Sec. 5] came out of the implementation, both recorded where they
matter (`PITFALLS.md` [Sec. 2] and [Sec. 7]):

- **The material comes from the site, not from Niko's hands.** [Sec. 1] only required a
  `build_cost` in data and the "no material" refusal. A build uses the surface material of the tile
  it stands on, so nothing new had to be invented in `objects.toml` and the eleven object kinds
  stay eleven; a material with no `build_cost` is not a building material, which is the
  "no building material" reason. A later phase can make the material travel as a carried object.
- **The menus golden is not regenerated.** `build` did not exist in the Python server, so
  `MenuGoldens` drops the ops added after the cut-over from both sides of the comparison instead of
  rewriting a fixture that no longer has a producer. Every other entry still has to match Python.

## 11. Out of scope

- **Halves and diagonals.** Phases 2 and 3, each its own doc. Phase 1 leaves `slot_mask` at zero
  everywhere, so the region graph is not built yet.
- **Per-chunk A* invalidation.** A `sim.engine` change to be measured, not assumed.
- **A 0.5 m build grid.** Rejected: it is uniform but loses the diagonals for good, since
  re-deriving them later would mean moving every wall.
- **Structural collapse, floors carrying weight, doorways as placed objects.** A doorway stays an
  edge flag and an object kind.
- **Who builds.** Niko builds by hand in this phase. Organizations, generated buildings and the
  plan-of-ops that places a house are the NPC-construction question in `docs/PENDING.md`, which
  needs needs, tasks and ownership first.
- **Refusing a build by distance is not a wall**: reach is the existing rule, as for `dig`.

---

## TL;DR

`build` is already in `ops.toml` with no handler, and wall edges already exist in the world as
canonical north and west edges that block movement, take damage and render. So phase 1 is the op,
the cost, the menu entry for a bare edge, and a real migration runner (`EnsureSchema` rejects
anything but the head today). The geometry is designed in full: 6 slots per tile, `N` and `W` on
the edges plus the interior halves `H`/`V` and diagonals `D1`/`D2`, as a bitmask on `chunk_level`
so the region-aware pathfinder of phase 2 has its cache key. Demolition is `break`, which already
works.
