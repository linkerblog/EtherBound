# Dev-012: Objects, the Matter primitive (Server + Web)

[Feature] [Primitive] [World] [Engine] [Rendering] [UI]

The first of the eight primitives as data (`docs/utils/VISION.md` [Sec. 6], "Matter with
properties"). Until now the world is terrain, floors and walls only. After this doc it also holds
**objects**, meaning items, containers and furniture:

- Objects are defined as data and made of registered materials.
- They occupy real volume, so they block the way, can be climbed and can be stacked.
- They are carried in two hands or worn.
- The first handling ops use them: `take`, `drop`, `put`, `open`, `close`, `wear`, `remove`, and
  `inspect` on objects.

`dig` gets its promised tool (`docs/done/Dev-007.md` [Sec. 1], "Hand digging").

Tile physics is `Dev-013` and is not written yet. This doc already stores what physics will need
(mass, material, bulk and an `integrity` column) so that `Dev-013` does not have to change what
an object means. The physics decisions approved on 23/09/2026 are recorded in
`docs/utils/VISION.md` [Sec. 5].

Reference: `docs/utils/VISION.md` [Sec. 2] (pillars), [Sec. 5] (world model, physics),
[Sec. 6] (primitives), [Sec. 7] (ops × properties); `docs/done/Dev-007.md` (op vocabulary,
handler contract, activities, `dig`, `climb`); `docs/done/Dev-002.md` (standing rule, sparse
levels); `docs/utils/STYLEGUIDE.md` [Sec. 5], [Sec. 8], [Sec. 12]; `CONTEXT.md`.

## 1. Decisions (approved 23/09/2026)

| Topic | Decision | Why |
|---|---|---|
| Kind and instance | An object is an instance of a **kind**. Kinds are data in `server/src/etherbound/world/objects.toml`. An instance carries only what varies: location, quantity, state, integrity and owner | Pillar 1. Ops read properties, never kind names. A new object is a new TOML row, not new code |
| Components | A kind's properties are flags (`solid`, `surface`, `fixed`, `stackable`) plus optional **components** (`container`, `openable`, `wearable`, `tool`). A handler's `applies` and `validate` read components only | The litmus test of VISION [Sec. 6]: `open` exists wherever `openable` is, so nobody writes a menu for a chest |
| Real volume (A1) | A `solid` object fills the half-metre cells above its resting surface. A `surface` object's top is a standing and placing surface. Chests can be stacked and climbed, and a table can be stood on, without any special case | Pillar 2: people climb tables and stack boxes. The standing rule, A* and prediction already work in half-metre cells, so objects only add cells |
| Carrying (B1) | Two hands plus worn slots (only `back` in this doc). A backpack is a container that is worn. Bulky objects (more than 25 l) take both hands. The lift limit is 40 kg per take, and the total carried mass slows walking | Real life, the Zomboid model. No abstract inventory grid |
| Stacks | Identical objects (same kind, location, state, owner and integrity, on a `stackable` kind) are one row with `quantity`. `take` splits one off. `put` and `drop` merge into an identical stack at the destination | Twenty cans are not twenty rows, and ownership still survives a split |
| Owner | Nullable `owner` column (an actor id now, an organization id later). No rule reads it yet | Primitive 6 ("steal" is `take` on an owned object, Dev-007 [Sec. 1]). The data exists before the law does |
| Physics fields (C1, D1) | Kinds carry `mass` (kg), `bulk` (litres) and `material`. Instances carry a nullable `integrity` (NULL means intact). Nothing in this doc lowers it | `Dev-013` defines cumulative damage in SI units on these fields without migrating their meaning |
| Hidden contents | The client receives only objects that lie directly on a tile. The contents of a container reach the player only through the menu, and only while it is open (or has no lid) and within reach | Pillar 3: you know what you can see. A closed chest does not leak its contents over the wire |
| Durations | Every op in this doc is instant: seconds are below the 1-minute clock | Real life: taking a bottle takes seconds. Activities stay for work that takes minutes |
| Tools | `dig` uses the best `tool.dig` factor among the objects in the actor's hands. With bare hands the factor is 0.25 | Fulfils Dev-007's "tools come with the objects doc". Digging with bare hands is about four times slower than with a shovel |
| One facing | Every sprite has a single facing, from BitCanvas pixel-style furniture. Four facings are a later BitCanvas doc | Agreed. Rotation is not needed to prove the primitive |
| Heights | Kind heights are whole half-metres. A `surface` sprite's top must match its height exactly, so BitCanvas `chest` and `barrel` grow from 0.75 m to 1 m | Otherwise Niko floats 8 px above the lid. A 1 m barrel is also a real barrel |

## 2. Data

### 2.1 New materials (`server.world`)

Append these to `materials.toml`. Ids are append-only, and `_sync_materials` assigns them. The
`resistance` values follow today's unitless scale; `Dev-013` redefines the unit for every
material at once.

| key | name | color | walkable | walk_cost | solid | blocks_sight | diggable | dig_cost | flammable | density | resistance | tags |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| `wood` | Wood | `#8a5a34` | true | 1.0 | true | true | false | 10.0 | true | 0.6 | 3.0 | `object` |
| `metal` | Metal | `#8c9399` | true | 1.0 | true | true | false | 10.0 | false | 7.8 | 9.0 | `object` |
| `cloth` | Cloth | `#5d6b4e` | true | 1.0 | true | false | false | 10.0 | true | 0.3 | 0.5 | `object` |
| `food` | Food | `#b8402f` | false | 1.0 | true | false | false | 10.0 | false | 1.0 | 0.2 | `object` |

`liquid = false` for all four. `walkable` matters only for `surface` tops, which use their
kind's material.

### 2.2 Kind catalog (`server.world`)

New module `world/objects.py`, next to `materials.py`:

- `ObjectKind` is a frozen dataclass: `key`, `name`, `material` (key), `mass`, `bulk`,
  `height` (half-metres; 0 when not solid), `solid`, `surface`, `fixed`, `stackable`,
  `container: Container | None` (`capacity` in litres), `openable: bool`,
  `wearable: Wearable | None` (`slot`), `tool: Tool | None` (`dig`).
- `ObjectCatalog.load(path=None, registry)` validates the file and raises on any error:
  - unique keys and a registered material;
  - `height > 0` exactly when `solid`;
  - `surface` requires `solid`, and a `surface` material must be `walkable`;
  - `stackable` excludes `container`, `openable` and `solid`;
  - `openable` requires `container`;
  - `wearable.slot == "back"` (the only slot);
  - `tool.dig > 0`;
  - unknown keys or components are rejected, so a typo is never silently ignored.
- Keys are stored as text in the `object` table, so renaming a kind needs a migration. The kind
  is not a blob id like a material.

`objects.toml`, the v1 catalog:

| key | name | material | mass kg | bulk l | height | flags | components |
|---|---|---|---|---|---|---|---|
| `chest` | Chest | wood | 15 | 120 | 2 | solid, surface | container 100, openable |
| `barrel` | Barrel | wood | 12 | 160 | 2 | solid, surface | container 150, openable |
| `table` | Table | wood | 20 | 400 | 2 | solid, surface | — |
| `chair` | Chair | wood | 5 | 150 | 2 | solid | — |
| `shelf` | Shelf | wood | 30 | 300 | 3 | solid | container 60 (no lid) |
| `backpack` | Backpack | cloth | 1 | 25 | 0 | — | container 20, openable, wearable back |
| `shovel` | Shovel | metal | 2 | 6 | 0 | — | tool dig 1.0 |
| `bottle` | Bottle | glass | 0.4 | 1 | 0 | stackable | — |
| `apple` | Apple | food | 0.2 | 0.3 | 0 | stackable | — |

TOML shape, one example; the rest follow it:

```toml
[[kinds]]
key = "chest"
name = "Chest"
material = "wood"
mass = 15.0
bulk = 120.0
height = 2
solid = true
surface = true

[kinds.container]
capacity = 100.0

[kinds.openable]
```

Derived quantities, all in `objects.py` and shared by every handler:

- `total_mass(obj)` = `mass × quantity` + the `total_mass` of its contents (recursive, depth cap 8).
- `total_bulk(obj)` = `bulk × quantity`. Contents do not add bulk, because a container's own
  bulk already includes its inside.
- `two_handed(kind)` = `bulk > 25`.

## 3. Storage (`server.db`)

Migration `0005_object` creates table `object`:

| Column | Type | Notes |
|---|---|---|
| `id` | Integer pk, autoincrement | Stable identity. Split stacks get a new id |
| `kind` | String(64), not null | Kind key |
| `loc` | String(8), not null | `tile`, `in`, `held` or `worn` |
| `x`, `y`, `h` | Integer, nullable | Set only when `loc = 'tile'`. `h` is the resting surface |
| `cx`, `cy` | Integer, nullable, index `(cx, cy)` | Derived from `x, y` for `tile`. Feeds the chunk payload |
| `container_id` | Integer, nullable, FK `object.id`, index | Set only when `loc = 'in'` |
| `actor_id` | String(64), nullable, FK `actor.id`, index | Set only for `held` and `worn` |
| `slot` | String(8), nullable | `left`, `right` or `both` (held); `back` (worn) |
| `quantity` | Integer, not null, default 1 | `> 0` |
| `state` | JSON, not null, default `{}` | `{"open": bool}` for `openable` kinds, nothing else yet |
| `integrity` | Float, nullable | NULL means intact. Reserved for `Dev-013` |
| `owner` | String(64), nullable | No rule reads it yet |

A `CHECK` constraint enforces that exactly the columns of its `loc` are set. The upgrade from
`0004` must keep an existing save; the new table starts empty, and `ensure_world` fills it
[Sec. 8]. `new_game` deletes every object before it deletes actors.

The Pydantic side (`engine/actions.py` or a new `engine/objects.py`) models the location as a
union discriminated by `kind`: `TileLoc {x, y, h}`, `InLoc {object_id}`,
`HeldLoc {actor_id, hand}` and `WornLoc {actor_id, slot}`. Events and payloads use this union.

## 4. World rules

### 4.1 Volume and surfaces (`server.world`, mirrored in `web.world`)

- A `solid` object resting at `h` occupies cells `h+1 … h+height`. This is the same convention as
  a body, which occupies `h+1 … h+3`.
- `WorldGrid` keeps an in-memory per-chunk index of the objects that lie directly on tiles:
  id, kind, x, y, h, quantity and `open`. From the solid ones it derives per-tile volumes. The
  engine updates the index after every committed object change, as it does after `lower_ground`.
- `solid_at(x, y, h)` returns true inside any object volume.
- `standing_surfaces(x, y)` adds the top `h + height` of every `surface` volume, using the kind's
  material and the usual 2 m headroom. The ground or floor under a solid object loses its
  headroom and stops being standable, so walking onto a chest's tile is impossible, not special
  cased.
- `climb` needs no change: a chest top 1 m above the ground is an ordinary Δh 2 standing surface.
  The acceptance tests prove it.
- **Resting surfaces** (new `resting_surfaces(x, y)`) are where an object can be placed:
  standable surfaces without the headroom requirement, plus `surface` tops. A placed object needs
  its own cells free (`h+1 … h+max(height, 1)`) and, if it is solid, no actor standing on that
  surface.
- **Support.** An object supports something when another tile object rests at its top, or an
  actor stands on its top. A supporting object cannot be taken, and an `openable` one cannot be
  opened: a chest with a bottle on its lid stays shut, which is real life. Falling objects are
  `Dev-013`.

### 4.2 Reach (`server.engine`)

The target tile is within `in_close_reach` (own tile, or an orthogonal neighbour with no wall at
the actor's `h`). The target's resting `h` (or the destination `h`) must be within
`[actor.h − 2, actor.h + 3]`, meaning from 1 m below the feet to 1.5 m above them. Carried
objects and the contents of worn containers are always within reach.

### 4.3 Hands and load (`server.engine`, mirrored in `web.net`/`web.world` prediction)

- A taken object goes to `right` if free, else `left`. A `two_handed` object needs both hands
  free and takes `slot = both`.
- The lift limit is 40 kg of `total_mass` per take. Without stats, this is a fit adult's limit.
  When Niko's stats and Ether exist, they replace the constant.
- `load_kg` is the `total_mass` of everything the actor holds and wears. The walking speed
  multiplier becomes:

  ```text
  load_multiplier = 1                               if load_kg <= 10
                    max(0.5, 1 - (load_kg - 10)/60) otherwise
  ```

  It is applied in `movement.py` next to the slope and material cost, and identically in client
  prediction. The engine caches `load_kg` per actor. It recomputes the value after every object op
  and at startup, never per movement input.

## 5. Ops (`server.engine`)

### 5.1 Contract changes

- `Target` gains `ObjectTarget {kind: "object", id: int}`.
- `OpHandler.build(ctx, target) -> Action` becomes
  `builds(ctx, target) -> Sequence[Action]`, so one target can produce several entries (put
  *this* bottle or *that* apple into the chest). The five existing handlers return `(action,)`.
- `OpHandler` gains `subject(ctx, action) -> str | None`, default `None`. `MenuEntry` gains
  `subject: str | None`, for example `"Bottle ×3"` or `"Bottle into Chest"`.
- Menu candidates in `WorldEngine.menu`:
  - the tile surface and `self`, as today;
  - every object lying on the tile whose `h // 6` equals the chosen surface's `z`;
  - the contents of those objects that are containers and are open or have no lid (one level
    deep);
  - on the actor's own tile, also every held or worn object and the contents of worn containers
    that are open.

  The order is catalog op order, then candidate order.
- Actions (all in the `Action` union, so they are generated into `schema.d.ts`):
  `InspectAction.target: TileTarget | ObjectTarget`, `TakeAction`, `DropAction`, `OpenAction`,
  `CloseAction`, `WearAction` and `RemoveAction` (each with `target: ObjectTarget`), and
  `PutAction {target: ObjectTarget, into: ObjectTarget | TileTarget}`.

### 5.2 Handlers

Reasons are the exact strings shown in `.why`. An op not listed as "applies" never appears.

| Op | Applies to | Refused when (reason) | Effect | Events |
|---|---|---|---|---|
| `inspect` | any candidate object | `out of reach` (30 m, as tiles) | Text: name, material, `open`/`closed`, and "holds N things" only when open or lidless. Held objects add their `total_mass` | none (Dev-007 rule) |
| `take` | object not held or worn, and not `fixed` | `out of reach`, `fixed in place`, `something is on it`, `too heavy` (> 40 kg), `hands full`, `closed` (source container closed) | Moves the object to the hands [Sec. 4.3]. From a stack, splits off 1 | `object.moved` |
| `drop` | held object | `no room` (a solid object would intersect the actor, or its cells are not free) | Puts it on the actor's standing surface and merges into an identical stack | `object.moved` |
| `put` | builds one entry per held object for each destination: an open or lidless container object (`into Chest`), a `surface` object's top (`onto Table`), or a tile surface (`here`) | `out of reach`, `closed`, `doesn't fit` (capacity by `total_bulk`), `no room`, `someone is there`, `not into itself` (container cycle) | Moves and merges | `object.moved` |
| `open` / `close` | `openable` object in reach, held or worn | `out of reach`, `something is on it` (open only), `already open` / `already closed` | Sets `state.open` | `object.changed` |
| `wear` | held `wearable` object | `slot taken` | Moves it to `worn` and frees the hands | `object.moved` |
| `remove` | worn object | `hands full` | Moves it to a free hand | `object.moved` |
| `dig` (changed) | as Dev-007 | new: `something is on it` (any object resting at the ground `h`) | Duration `ceil(30 × dig_cost / tool)`. `tool` is the best `tool.dig` among held objects, or 0.25 for bare hands. `dig_cost > 2` keeps its reason | as Dev-007 |

Every effect that changes a tile object bumps that chunk's `revision` (row and grid). It emits
`ChunkChanged`, and the hub re-sends the chunk as it does after `dig`.

### 5.3 Events (`server.events`)

| Type | Logged | Data |
|---|---|---|
| `object.moved` | yes | `object_id`, `kind`, `quantity`, `op`, `actor_id`, `from: Location`, `to: Location`, `split_from: int \| None`, `merged_into: int \| None` |
| `object.changed` | yes | `object_id`, `kind`, `op`, `actor_id`, `changes` (for example `{"open": true}`) |

Witnesses will subscribe to these later. They must carry who did what to which object, and
from where to where.

## 6. Protocol and API (`server.net`, `server.app`, `web.net`)

- `GET /api/objects` returns the kind catalog: key, name, material, mass, bulk, height, solid,
  surface, openable and container capacity.
- `ChunkPayload.objects: ObjectPayload[]` lists only objects lying on tiles: `id`, `kind`, `x`,
  `y`, `h`, `quantity`, `open` (null if not openable).
- `ActorState` (snapshot and tick) gains `carried: CarriedObject[]` (`id`, `kind`, `name`,
  `quantity`, `slot`) and `load_kg`. `ActionResult` gains the same two fields, so the HUD updates
  on the result instead of on the next tick.
- `MenuEntry.subject` [Sec. 5.1].
- Regenerate `server/schema.json` and commit `web/src/net/schema.d.ts`. Nothing is hand-written.

## 7. Client

### 7.1 `web.world`

- `ChunkStore` keeps each chunk's `objects` and the kind catalog, and derives per-tile volumes
  exactly as the server does [Sec. 4.1]. `hasHeadroom`, `standingH` and `walkCost` take object
  volumes and `surface` tops into account.
- Prediction multiplies by `load_multiplier(load_kg)` from the latest actor state.
- `pickTile` treats the top of each solid object like a floor top, so right-clicking a table
  picks the table's tile at its top.

### 7.2 `web.game`

- New `objectSprites.ts` (a pure kind → `{file, anchorX, anchorY}` table, testable in node) and
  `objectSheets.ts` (static imports, the Vite pitfall in `CONTEXT.md`). Sprites live in
  `src/sprites/object/<kind>.png`.
- Solid objects are drawn inside the same ordered `Blitter` batches as the terrain, never as
  separate `Image`s (`CONTEXT.md` pitfall). Each one is drawn in its tile's draw slot, after that
  tile's top at its resting `h` and its walls, and it follows the same split at Niko's feet. Object
  frames go into their own band of the runtime atlas, with the same 4096 px guard.
- A kind without a sprite is drawn as a placeholder prism: a top diamond plus S and E faces,
  `height × 16` px, in its material colour with the wall light (N 0.82, W 0.66).
- Non-solid objects on a surface draw one small **pile marker** per `(x, y, h)`: a 12×6 px
  diamond in the top object's material colour.
- Cutaway: an object is drawn only if its resting surface is drawn.

### 7.3 `web.ui`

- The menu renders `label` followed by `subject` (`› Take Bottle ×3`, `› Put Bottle into Chest`).
  `.why` is unchanged. Add the rule to `docs/utils/STYLEGUIDE.md` [Sec. 8].
- New `CARRY` HUD panel above the meters, with rows `L`, `R` (or one `HANDS` row for `both`),
  `BACK`, and `LOAD 12.4 kg`. The value of `LOAD` turns amber above 10 kg, where slowing begins.
  Add it to `docs/utils/STYLEGUIDE.md` [Sec. 5] and [Sec. 12].
- The feed shows each result's `text` as an `act` line (`Taken: Shovel (right hand).`).

### 7.4 `bitcanvas`

- In `pixelart.js`, scale every z coordinate of `chest` and `barrel` by 4/3 (extent 24 → 32),
  so their tops sit exactly at 1 m [Sec. 1]. The other pieces stay byte-identical.
- Export `table`, `chair`, `chest`, `shelf` and `barrel` in pixel style (seed `A17F3C`, first
  palette) through the existing download, and save them as `src/sprites/object/<kind>.png`.
  Sending objects from BitCanvas is out of scope.

## 10. What must not break

- The engine is the only writer. Object ops go through `submit`, and the menu stays a read.
- Menus are generated. No handler checks a kind key, only flags and components.
- Server and client standing rules stay in parity. Every server volume test has a client twin.
- Existing saves upgrade through `0005_object` without a wipe. Actors keep their position or are
  relocated by the existing rule.
- `move`, `wait` and `climb` behave as before on tiles without objects. `dig` changes only its
  duration (tools) and the new refusal.
- Contents of closed containers never appear in a chunk payload, snapshot or tick.
- Terrain draw order, cutaway and picking are unchanged where there are no objects.
- The other BitCanvas pieces and sheets stay byte-identical.

## 11. Acceptance

**Automated (server):**

1. The catalog loads. Each validation rule of [Sec. 2.2] rejects a broken fixture.
2. Grid: a chest on ground `h` makes that tile's ground unstandable and its top standable at
   `h + 2`. A* goes around it. `climb` reaches the top from an orthogonal neighbour and climbs
   down again. On the stacked pair the upper chest covers the lower lid, so walking from one top
   to the other is impossible and only the upper top is standable; climbing it from an orthogonal
   neighbour at `h + 1` (a Δh 3 step) works, and climbing back down does too.
3. Each reason of [Sec. 5.2] is produced by a minimal fixture. Each effect commits the right
   location, slot, quantity and events, and bumps the chunk revision.
4. Stacks: taking from `apple ×3` leaves `×2` and creates a new row with `split_from`. Dropping
   it back merges (`merged_into`), and the row count returns to the start.
5. Load: carrying 40 kg gives multiplier 0.5 in `move_in_world`. With 10 kg or less, movement is
   unchanged.
6. `dig` topsoil takes 24 minutes with a shovel in hand and 96 with bare hands, and is refused
   with an apple on the tile.
7. A closed chest's contents are absent from `chunk_payload`. After `open`, they appear in the
   menu as candidates.
8. Migration: a `0004` database with an actor upgrades, keeps the actor, and gains the v4
   objects.
9. `pytest`, `ruff check`, `ruff format --check` and `pyright` pass.

**Automated (web):**

10. `ChunkStore` object-volume parity cases mirror 2. `pickTile` hits a table top.
    `objectSprites` entries all have an import. `npm test` and `npm run build` pass, and the
    generated types are committed.

**Manual (live game):**

11. The chest, shelf, table, chairs and barrel render as sprites. Niko walking behind and in front
    of a chest is occluded and drawn in the right order.
12. Take the shovel: the `CARRY` panel shows it. Dig a tile, which now takes the shovel's time.
13. Wear the backpack, open the chest, and put apples into the backpack. Check `LOAD`. Close the
    chest: its contents leave the menu.
14. Climb onto the stacked chests and back down. Put a bottle on the table.
15. Take the chest (both hands): walking is slower, and `take` on anything else says
    `hands full`.

## TL;DR

Objects become data: kinds in `objects.toml` with flags and components, made of four new
materials. Instances live in a new `object` table with one location (tile, inside, held or worn),
stacks, state, owner and a reserved `integrity`. Solid objects fill half-metre cells, so they
block, can be climbed and can be stacked, with server/client parity. Niko carries objects in two
hands and on the back, and load slows him. Seven instant handling ops arrive (`take`, `drop`,
`put`, `open`, `close`, `wear`, `remove`) plus `inspect` on objects, with generated menus that
name their subject. `dig` uses held tools. Sprites come from BitCanvas with one facing. The test
world v4 places a chest, a backpack, a shovel, furniture and a stacked pair. Physics is `Dev-013`.
Project `v0.7.0`.
