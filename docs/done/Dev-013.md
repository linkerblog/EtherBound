# Dev-013: Tile Physics

[Physics] [World] [Engine] [Events]

Implement the tile-based physics decisions in `docs/utils/VISION.md` [Sec. 5]. Physics resolves
inside the action submit, commits one deterministic outcome and its event log, and leaves animation
to the client. It does not add a continuous physics tick or let the physics code apply health.

Reference: `docs/utils/VISION.md` [Sec. 5] (physics decisions), [Sec. 7] (shared ops);
`docs/done/Dev-012.md` (object mass, materials and reserved integrity); `docs/done/Dev-007.md`
(action handlers and event pipeline); `CONTEXT.md`.

## 1. Accepted design

| Topic | Decision | Why |
|---|---|---|
| Resolution | Each push, pull, drag, throw, hit or break resolves its complete trajectory in one `submit`. The committed event contains the server-computed path; there is no per-tick physics state | The clock is 1 Hz and cannot represent sub-second impacts |
| Units | Mass is kg, speed is m/s, impulse is N·s, energy and integrity are J; kinetic energy is `0.5 × mass × speed²`, gravity is `9.81 m/s²` | SI units make the material calibration and collision outcomes interpretable |
| Strikes | A held data-defined `Tool.strike_speed_m_s` and its mass determine strike energy; bare hands use the standardized physics-profile values | One formula serves every tool kind without special cases |
| Effort | Shove speed is 2 m/s with reduced mass; throw is capped at 8 m/s and 100 J; a bare hand is 2 kg at 5 m/s; horizontal loss per metre is `0.05 × mass × 9.81` J | Fixed profiles keep action-time paths bounded, deterministic and testable |
| Material resistance | `Material.resistance` is the energy in joules required to break one half-metre segment of that material. Recalibrate the TOML values against the three cases in VISION: a fist does not break brick, a sledgehammer needs several blows, and a car at 50 km/h passes through | The existing float column is sufficient; only its documented unit changes |
| Cumulative damage | `Object.integrity` stores remaining joules; NULL means intact at the kind's derived maximum. Wall-edge integrity is stored sparsely by canonical north/west edge and level. Each collision subtracts the energy absorbed; zero converts an object to rubble or turns a wall edge into an opening | Damage survives save/load without storing untouched edges |
| Falling | Unsupported objects and bodies fall to the next supported surface during the same resolution. The event records the vertical path and `impact` carries the potential energy converted at landing | Falls must be visible to subscribers without physics knowing health |
| Impacts and health | Physics emits a logged `impact {target, energy}` fact. A body/health subscriber may later convert it to injury; this phase does not modify health | Preserves system boundaries while making impacts replayable |
| Ownership | Only `WorldEngine` mutates actor, object, wall and chunk state. Subscribers observe committed facts; they never resolve or write physics outcomes | Keeps one state writer and atomic event logging |
| Client | The server returns the authoritative path with the action result. The client animates that path and never re-simulates collision or damage | Replay and prediction must not invent a second physics rule set |

## 2. Data and engine

### 2.1 Persistence

- Reuse `Object.integrity`; its value is remaining J. Derive full integrity from the object's
  material resistance and solid height (in half-metre units); non-solid objects use one unit.
- Add migration `0006_physics` with positive `Actor.mass_kg` (80 kg for existing actors) and sparse
  wall-edge damage keyed by chunk, level, cell and owned edge (`north` or `west`). Existing wall
  material arrays remain the source of whether an edge is present and which material it uses.
  Breaking an edge clears that existing array cell and removes its damage row in the same
  transaction.
- Reuse the material table's existing `resistance` float. Material TOML values and their tests use
  the new J-per-half-metre unit. Existing saves keep stable material IDs; startup reads resistance
  from the registry and must not rely on stale persisted values.
- Rubble is a data-defined object kind. When an object breaks, preserve its location, release
  container contents onto the same supported surface, and replace the broken instance with rubble.

### 2.2 Actions and resolution

- Add typed wall-edge and actor targets to the shared action contract, and add physics actions for
  `push`, `pull`, `drag`, `throw`, `hit` and `break`. Menus offer only applicable, validated actions;
  `submit` repeats validation before mutation.
- Push/pull/drag resolve the target's complete tile-by-tile path. Throw uses an explicit normalized
  direction and starts from a held object. Hit/break resolve an impact against an object, actor or
  wall edge using the source's mass, velocity/impulse and the target material's resistance.
- Stop a trajectory on a surviving obstruction; if the obstruction breaks, continue with remaining
  energy. Resolve falls after support is removed and preserve deterministic collision/event order.
- Each changed chunk updates its grid and database row and emits the existing unlogged
  `ChunkChanged` replication signal. The logged physics event carries the complete path, impacts,
  damage and break outcomes needed for replay.
- Include the committed path in the action result/WebSocket contract and have Phaser animate only
  those server-provided positions.

## 3. What must not break

- The engine is the only writer; physics never writes state from an event subscriber.
- A failed validation changes nothing and emits no event.
- State changes and logged physics events commit atomically and use the engine's global event order.
- Equal seed, state and submitted actions produce the same path and damage; no unseeded randomness or
  wall-clock input is used.
- Existing object handling, standing rules, movement, chunk streaming and old saves remain valid.
- Client animation consumes server results and does not decide collision, damage, falling or paths.
- Physics emits impacts but does not apply health or injury.

## 4. Acceptance

### Automated

1. Unit tests verify kinetic/potential energy, energy conservation across collisions, and resistance
   calibration against the three reference cases in [Sec. 1].
2. Engine tests cover push, pull, drag, throw and hit; wall/object cumulative damage; break-through
   with remaining energy; and deterministic multi-collision paths.
3. Falling tests cover objects and bodies, landing surfaces, impact energy, the greater-than-3 m
   body impact threshold and unsupported terrain.
4. A wall with partial damage survives engine restart with the same integrity; breaking it clears
   the wall cell and allows movement through it. Migration `0006_physics` upgrades a `0005` save
   without wiping actors, chunks, levels, objects or events.
5. Event tests assert path, impact, damage and break events are logged in commit order and that
   replication-only chunk changes are not persisted.
6. Web tests assert the action result exposes the server path and the scene animates it without
   deriving a second trajectory.

### Manual

7. In the running game, push and throw objects into an obstacle, break a wall over repeated hits,
   and watch an object fall into the pit. The animation must match the committed final positions and
   the scene must remain responsive at x1–x4.

## TL;DR

Implemented action-time tile physics in SI units, with cumulative damage, persistent wall integrity,
falls, impacts and replayable server-computed paths. The engine commits everything atomically;
subscribers may interpret impacts but physics does not apply health. Existing object integrity is
reused and sparse wall damage ships in migration `0006_physics`.
