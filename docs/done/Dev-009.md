# Dev-009: Keys typed in the LLM tab

[Feature] [LLM] [UI] [Security]

Today the two keys (TypeSafe for Jev, OpenRouter for the narrator) can only come from environment variables or from a
hand-edited `llm.json`, and `Dev-008.md` D2 says a key is "never editable or readable from the UI". This plan changes
the first half of that rule on purpose: the LLM tab gets a masked, **write-only** box per key, so the player pastes a
key into the game, it is saved, and free text and the narrator start working with no restart. The second half stays:
no key is ever shown, logged, put in an event or a frame, or kept in the HUD after it is saved.

## 1. Findings

Read from the source; nothing here was run.

- **Keys are read once.** `LlmRuntime.Create` builds `TypeSafeJev`, `OpenRouterChat` and the `Narrator` from the keys it
  finds at startup, and the constructor builds the `FreeTextInterpreter` from that Jev. Nothing can swap them later.
- **The host already reads them fresh.** `SimulationHost.Llm.cs` reads `_llm.Interpreter` and `_llm.Narrator` at each
  use, never caching them, so a runtime that can replace them is enough; the host needs no change.
- **A key's source order is the opposite of a model's.** `LlmConfig.Load` takes the environment first and the file
  second; `RoleRegistry` takes the tab first, then the environment. A key saved in the game would lose to a stale
  environment variable and look broken.
- **The file side exists.** `LlmConfig.SaveRoles` already rewrites `llm.json` atomically and keeps every other key, and
  `RoleRegistryRules` asserts it never invents a key. Saving keys is the same operation on other fields.
- **The tab is already key-safe.** `LlmTabModel` reports "set or not set" only, and `LlmTabRules` asserts no key appears
  in anything it builds. The HUD rebuilds itself when the window scale changes, so a field's text must never be state.
- **Not checked.** Whether OpenRouter's `GET /api/v1/auth/key` (key info, no tokens spent) still exists and what it
  returns was written from memory; the Test button of D4 depends on it.

## 2. Decisions

Marked **approval needed** where the choice is open.

- **D1. Where a key is stored.** `llm.json` in the user data directory, as plain text, the same file and exposure as
  the environment-variable route and NikoStory's `.env`. The folder is per-user and outside the repo. **Approval
  needed:** the alternative is Windows DPAPI (`ProtectedData`, current user), which encrypts the key at rest but is
  Windows-only and makes a copied save folder silently lose its keys. Recommended: plain text now, DPAPI as its own
  Dev if wanted.
- **D2. The box is write-only.** A `LineEdit` with `Secret = true`. After Save the box is cleared and loses focus, and
  the row reads `SET · SAVED IN GAME` or `SET · FROM ENVIRONMENT` or `NOT SET`. No last four characters: they are
  still part of the secret. The pasted text is never held in `GameHud` or `LlmPanel` state, so a HUD rebuild cannot
  bring it back.
- **D3. A saved key beats the environment.** Same order as a model: the tab, then the environment. Otherwise a stale
  `OPENROUTER_API_KEY` would silently override what the player just typed. `Remove` deletes only the saved key and
  the environment's one applies again; the row says which one is live. **Approval needed:** the other order (the
  environment wins and the box is disabled while it is set) is safer for someone who manages keys outside the game
  but surprises the player who types one.
- **D4. A Test button.** Per key, one cheap real call that says `OK` or the scrubbed error: Jev asks one trivial `noul`
  question; OpenRouter calls the key-info endpoint (no tokens, no cost). The result is a line in the tab, never an
  event. **Approval needed:** drop the button if the OpenRouter endpoint cannot be confirmed (see [Sec. 1]); the
  fallback is a one-token completion with the narrator's model, which needs a model to be set.
- **D5. Validation before saving.** Trimmed, 8 to 256 characters, printable ASCII with no spaces or line breaks;
  anything else is refused with a reason and nothing is written. A key the vendor later rejects shows up as the
  usual "NARRATOR OFFLINE" or "free text unavailable" line, never as a crash.
- **D6. Hot swap.** `LlmRuntime` holds its Jev, interpreter, chat client and narrator behind one lock and exposes
  `SetKeys(typeSafeKey?, openRouterKey?)`. A call already in flight keeps the client it started with; the next call
  uses the new one. The shared `HttpClient` is kept. Removing a key puts `NoJev` or no narrator back.
- **D7. The existing rules that stay.** No key in a frame, event, log line, `llm_call` row, exception message,
  screenshot or test snapshot; `Narrator` and `FreeTextInterpreter` still fail closed without a key; the world engine
  never sees a key.

## 3. Changes

- `sim.llm`: `LlmConfig.SaveKeys` and `RemoveKey` (read-modify-write like `SaveRoles`, atomic, other fields kept);
  `Load` takes the file before the environment for keys and reports each key's source (`saved`, `environment`,
  `none`); a `KeyCheck.Validate` for D5; `LlmRuntime.SetKeys`, `KeySource`, and `Test` (D4).
- `game.ui`: `LlmPanel` gets one masked `LineEdit` plus `SAVE`, `REMOVE` and `TEST` per key; `LlmTabModel` gains the
  source text and the validate-then-apply path; the hint line is reworded.
- Docs: `Dev-008.md` D2 is amended (the key becomes write-only), `CONTEXT.md` "Models" contract, `PITFALLS.md` section 8
  (a secret box must not survive a HUD rebuild), `docs/utils/VERSION.md`.

## 4. What must not break

- A key is never readable from the UI: no echo, no tooltip, no last characters, no copy-out.
- Environment-only setups keep working: with no saved key the environment applies exactly as today.
- Saving a key never touches the role choices in `llm.json`, and saving a role never touches a key.
- A failed write leaves the previous file intact (temp file, then move) and says so in the tab.
- The world engine is the only writer of state; nothing here is journaled or replayed.

## 6. Out of scope

showing balances or limits, editing the Jev model, and sending keys anywhere but the vendor's own endpoint.

## TL;DR

Keys get masked, write-only boxes in the LLM tab: paste, Save, and free text and the narrator start with no restart,
because `LlmRuntime` learns to swap its clients. A saved key beats the environment and the row says which one is live;
a key is validated, stored in `llm.json`, and never shown, logged or kept in the HUD. This amends Dev-008's "never
editable from the UI" to "write-only", which is why it waits for approval.
