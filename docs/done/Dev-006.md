# Dev-006: New game button (Web client)

[Feature] [UI] [Bugfix]

Adds a `NEW` control to the HUD. It asks for confirmation and a seed, then calls the existing
`POST /api/game/new`. Today that endpoint is only reachable with `curl`, and even then the open
client does not redraw the new world [Sec. 1.1]. This doc fixes that too, because without the fix
the button would show the old city. The server does not change.

Reference: `docs/utils/STYLEGUIDE.md` [Sec. 5-7] (HUD panels, clock toolbar, buttons) and
[Sec. 16] (keyboard path); `CONTEXT.md` (REST, WebSocket); `docs/Fix02.md` H2 item 4, which
this makes testable from the GUI. `utils/VISION.md` is not affected.

## 1. Current state

### 1.1 The client keeps the old world after `new_game` (bug)

- The server regenerates every chunk with `revision = 0` (`world/chunk.py` [line 83]). The hub
  resends them after `world.generated` (`net/ws.py`, `reset_world`).
- `ChunkStore.set` (`web/src/world/ChunkStore.ts` [line 57]) drops a chunk when
  `previous.revision >= chunk.revision`. The store already holds revision 0 for every key, so it
  **drops every regenerated chunk**, and the old tiles stay on screen.
- `MapScene` clears the store only when `genVersion` changes (`MapScene.ts` [lines 118-124]).
  `new_game` keeps `gen_version = 2`, so that never happens. The prediction also keeps Niko's old
  position until an ack corrects it.
- Result: after `new_game` the screen shows the previous world until a page reload. Dev-005
  acceptance item 4 ("the client redraws the new world without a reload") cannot pass.

### 1.2 What the client knows

`WorldState` (`web/src/net/protocol.ts` [line 15]) has no `seed`, although every `snapshot`
carries one (`schema.d.ts`). `WebSocketClient` merges `snapshot` and `tick` into one `onState`
stream, so no listener can tell a fresh world from an ordinary tick.

## 3. What gets built

### 3.1 `web.net`: `web/src/net/protocol.ts`, `client.ts`

- `WorldState` gets `seed?: number`. `readWorldState` reads `payload.seed` and otherwise keeps
  `previous.seed` (a tick carries no seed).
- `WebSocketClient.onSnapshot(listener: (state: WorldState) => void): () => void`. In `receive`,
  for a `snapshot`, update `this.world`, call the **snapshot listeners first**, then the state
  listeners. A `tick` calls only the state listeners, as today.
- New `requestNewGame(seed: number): Promise<void>` in `client.ts` (or in a small
  `web/src/net/api.ts`, if the implementer prefers to keep REST out of the socket class). It
  POSTs `{ seed }` as JSON to `/api/game/new` and throws `Error("new game request <status>")` on a
  non-2xx response. It ignores the response body: the snapshot is the source of truth.

### 3.2 `web.game`: `web/src/game/MapScene.ts`

- Subscribe with `client.onSnapshot(...)` in `create()` and unsubscribe in `shutdown()`, like the
  other listeners. The handler destroys every chunk layer, clears `chunkLayers` and
  `this.chunks`, and sets `hasAuthoritativePosition = false`. The `onState` listener, which runs
  right after for the same message, then resets the prediction and `viewerH` from the snapshot
  (existing code).
- Remove the `genVersion !== this.generation` branch and the `generation` field. `onState` keeps
  `setWorldInfo` and `applyCameraBounds`.
- Also reset `telemetryOrigin`, so the SPD readout does not show a jump from the old position to
  the spawn as speed.

### 3.3 `web.ui`: `web/src/ui/App.tsx`, `styles.css`

- Clock panel: after the speed buttons, `<span className="sep" />` and
  `<button className="mini" aria-haspopup="dialog" aria-expanded={open}>NEW</button>`.
- New `NewGamePopover` component, rendered inside `.hud` when open:

## 4. Traps

1. **Listener order.** The snapshot reset must run *before* `onState` handles the same message.
   Otherwise `onState` sees `hasAuthoritativePosition = true`, keeps the old position, and the
   reset then throws it away.
2. **Chunks can arrive right after the snapshot.** The hub sends the snapshot, then the chunks,
   on the same socket, in that order. Clear only on the snapshot, never on a later tick, or
   freshly received chunks get wiped.
3. **Late acks.** A move submitted just before `new_game` can be acknowledged after the snapshot
   and pull the prediction back to the old spot for one frame. The next ack corrects it. Do not
   add sequence-epoch logic for this.
4. **Numbers in `<input type="number">`.** `value` is a string, and `""`, `"1e3"` and `"-0"`
   parse unexpectedly. Validate with `/^\d+$/` and the range check before `Number(...)`.
5. **WASD while the popover is open.** `readDirection()` already ignores keys while an `input` has
   focus. With focus on a button, WASD moves Niko, and that is fine.
6. **Double submit.** Disable the buttons while the request is in flight. Enter pressed twice
   must not send two `new_game`s.
7. **Strict Mode.** `onSnapshot` must return its unsubscribe function and `MapScene.shutdown()`
   must call it, or the second mount leaves a listener attached to a destroyed scene.

## 6. What must not break

- WASD, prediction, reconciliation and chunk streaming while walking.
- Reconnect after a server restart: the snapshot now clears and refills the world. It must end
  in the same picture as before, with no flash of missing chunks beyond the reload.
- Pause, x1/x3/x10, zoom, right-click menu and the free-text input.
- A `new_game` sent with `curl` also redraws the open client (same snapshot path).
- The browser context menu stays suppressed.

## 7. Tests and checks

The web client has no test runner (Dev-004 [Sec. 6]). Checks:

```text
cd web && npm run gen:types && git diff --exit-code src/net/schema.d.ts && npm run build
cd server && uv run pytest && uv run ruff check && uv run ruff format --check && uv run pyright
```

Manual acceptance with `EtherBound.exe`:

1. `NEW` appears at the end of the clock toolbar. Tab reaches it, and Enter or a click opens the
   popover with the current seed selected in the field.
2. `CANCEL`, Esc and a click on the world close it without a request (no `POST /api/game/new`
   in `logs\server.log`).
3. `RANDOM` fills a different whole number. Typing `-1`, `2.5`, `abc` or an empty value shows
   the red error and sends nothing.
4. Confirm with seed 7. The old world disappears, the new one is drawn around Niko at the road
   spawn (121.5, 128.5) with no reload, the clock shows DAY 1 · 00:00 at x1, the feed shows
   `NEW GAME · SEED 7`, and WASD works right away.
5. `GET /api/events` restarts at `seq` 1: `world.generated` (`seed` 7), `actor.spawned`,
   `clock.changed`. This is Fix02 H2 item 4.
6. Walk 10 m: `actor.moved` rows appear. On the user's current save this also gets past Fix02
   H3, since the new spawn has an exact `h`. H3 still needs its fix for old saves.
7. Confirm again with the same seed: an identical world, Niko back at spawn, the log restarted.
8. Stop the server while the popover is open and confirm: the error shows in red, and the
   popover stays open.
9. Restart the server with the page open: after it reconnects, the world is redrawn once and
   is complete.
10. A second browser tab, connected to the same server, also redraws after the first one
     confirms.

The GUI acceptance was not run because confirming replaces the active single-slot save. It remains
tracked in `docs/PENDING.md` for a safe manual session.

## TL;DR

Adds a `NEW` button to the clock toolbar. It opens a confirmation popover with a seed field
(prefilled with the current seed, plus `RANDOM`), then calls the existing `POST /api/game/new`.
It also fixes the reason the open client never showed a regenerated world: chunks come back at
revision 0 and the store drops them, and the scene only reset when `gen_version` changed. Now
every `snapshot` resets the client world. `web.net`, `web.game` and `web.ui` change. The server
does not. Once it lands, Fix02 H2 item 4 can be run from the GUI.
