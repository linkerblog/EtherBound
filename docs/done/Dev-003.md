# Dev-003: Launcher executable (Tooling)

[Tooling] [Bugfix] [Infrastructure]

Replaces `start.bat`, the PowerShell supervisor and the batch wrappers with one native
`EtherBound.exe`. The batch chain fails in ways measured below [Sec. 1]; the executable removes
the causes instead of patching them: no shells, one hidden console per service, job objects that
Windows empties when the launcher ends, real health checks, and logs it writes itself. Nothing
under `server/` or `web/` changes.

Reference: `CONTEXT.md` (Commands, Measured pitfalls). `utils/VISION.md` is not affected.

## 1. Why the batch launcher fails

Measured on 2026-09-22 on the development machine; PIDs and log lines are real.

- **P1 — Ctrl+C becomes a prompt nobody can answer.** On Windows, uvicorn's reloader restarts its
  worker with `os.kill(pid, CTRL_C_EVENT)` (`uvicorn/supervisors/basereload.py`), and every
  process on that console receives it, including the hidden `cmd.exe` running `run-server.bat`.
  cmd answers with its "Terminate batch job (Y/N)?" prompt (localised, the last line of
  `logs/server.log`) and waits for a key forever. That `cmd.exe`, PID 13848, started on
  2026-09-21 at 23:11 and is still alive.
- **P2 — Cleanup misses it.** `scripts/stop.ps1` matches `uvicorn etherbound\.app:app` and
  `EtherBound\web\...vite`; the wrapper's command line (`call "...\scripts\run-server.bat" >
  "...\logs\server.log"`) matches neither. Closing the window also relies on PowerShell running
  `finally` while Windows tears the console down.
- **P3 — The leftover silently blocks the next start.** The run at 11:28 never started the server:
  PID 13848 still holds `logs/server.log` open (checked), the file still has the previous night's
  output, no server process from that run exists, and `web.log` shows
  `ECONNREFUSED 127.0.0.1:8000`.
- **P4 — `[ OK ]` is printed before anything runs.** There is no health check, and the loop in
  `launcher.ps1` watches the `cmd.exe` wrappers, not the services, until both are gone. A dead
  server is never reported.
- **P5 — Hot reload was switched off to dodge P1.** The uncommitted `run-server.bat` drops
  `--reload`; its comment blames stdin, but the traceback in `server.log` is a
  `KeyboardInterrupt`: the broadcast Ctrl+C.
- **P6 — npm adds more batch layers.** `npm run dev` runs `cmd.exe /d /s /c vite ...`, which runs
  the `node_modules\.bin\vite.cmd` shim (PID 27040 → `node` 34004). The same prompt can hang there.
- **P7 — Ports are not checked.** Anything on 8000 makes uvicorn exit; on 5173 Vite silently moves
  to 5174 (no `--strictPort`) while the banner still says 5173. And `stop.ps1` kills whatever
  listens on those ports, even another project's server.
- **P8 — Hygiene.** `mode con lines=32` cuts conhost's scrollback to 32 lines; logs mix the OEM
  code page with UTF-8 and keep Vite's ANSI colours (picocolors colours on Windows even when
  piped); the `.bat` files in the working tree have LF endings, which cmd.exe misparses in edge
  cases (agents write LF, `core.autocrlf` only converts on checkout); the banner's `0.0.1`
  matches nothing in `docs/utils/VERSION.md`.

### 3.2 Command line

```text
EtherBound.exe                   start and supervise server + web
    --no-reload                  server without hot reload
    --open                       open the game in the browser once both are ready
EtherBound.exe --cleanup         remove this checkout's leftovers, report other port owners, exit
EtherBound.exe --help
EtherBound.exe --ctrl-c <pid>    internal graceful-stop helper [Sec. 3.7]
```

Exit code 0 on a normal quit; 1 on a usage error, a failed preflight or a second instance.
`--help` and `--ctrl-c` skip the start-up sequence.

### 3.3 Start-up sequence

1. Parse arguments.
2. Root: walk up from the exe's folder to the first folder holding `server/pyproject.toml` and
   `web/package.json`.
3. Single instance: named mutex `Local\EtherBound.Launcher.<hash of the root path>`. Taken: say a
   launcher is already running for this checkout and exit 1.
4. Launcher job [Sec. 3.5]; open `logs/launcher.log`.
5. Tools: `uv.exe` and `node.exe` on `PATH`; `web/node_modules/vite/bin/vite.js` present, else
   print `cd web && npm install`. The server venv is left to `uv run`, as today.
6. Leftovers and ports [Sec. 3.8].
7. Rotate and open the service logs, start both services, report readiness.

A failure before step 7 prints the reason. If the console belongs to the launcher alone
(`GetConsoleProcessList` returns 1: it was double-clicked), wait for a key so the window does not
vanish.

### 3.4 Services

| | Server | Web |
|---|---|---|
| Executable | `uv.exe` from `PATH` | `node.exe` from `PATH` |
| Arguments | `run uvicorn etherbound.app:app --host 127.0.0.1 --port 8000` (never `--reload`: the launcher reloads, [Sec. 3.7]) | `<root>\web\node_modules\vite\bin\vite.js --host 127.0.0.1 --port 5173 --strictPort` (absolute, so the leftover rule recognises it) |
| Working dir | `server/` | `web/` |
| Extra env | `PYTHONUNBUFFERED=1`, `PYTHONIOENCODING=utf-8`, `NO_COLOR=1` | `NO_COLOR=1` |
| Ready when | `GET http://127.0.0.1:8000/api/health` returns 200 | `GET http://127.0.0.1:5173/` returns 200 |
| Log | `logs/server.log` | `logs/web.log` |

Vite starts from its JS entry, not through `npm run dev`: npm and `node_modules\.bin\vite.cmd`
are batch shims (P6). The `dev` script in `web/package.json` stays as the manual equivalent.

### 3.5 Process model

- **Launcher job.** Right after the single-instance check, create a job with
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and assign the launcher itself to it. Every process
  started afterwards belongs to it, so when the launcher ends by any path (Q, Ctrl+C, window
  closed, crash, Task Manager) Windows kills them all. This replaces every `finally` and every
  cleanup script. If the assignment fails, warn and rely on the explicit stop [Sec. 3.7].
- **Service jobs.** Each service also gets its own job, assigned while the process is still
  suspended (next bullets), so nothing escapes it; it nests inside the launcher job. Stopping a
  service terminates its job, which reaches every descendant even when its parent already died
  (a tree walk by parent PID misses those).
- **Job flags.** Kill-on-close only: no breakaway flag on either job, and non-inheritable handles
  [Sec. 4].
- **No shells.** Started straight from the executable. Never `cmd.exe`, `.bat`/`.cmd`, `npm`,
  `npx` or PowerShell (P1, P6).
- **One hidden console per service.** `CREATE_NO_WINDOW`: each service gets a windowless console
  of its own, so a Ctrl+C meant for one service never reaches the launcher or the other one. The
  launcher calls `CreateProcessW` itself (`Win32/ChildProcess.cs`) rather than `Process.Start`:
  `CREATE_SUSPENDED` until the process sits in its job, then resumed, and only its three pipe
  ends are inherited (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`), so neither service holds the other's
  pipes open.
- **Pipes.** stdout and stderr redirected and decoded as UTF-8. stdin redirected to a pipe that
  stays open for the service's whole life and is never written [Sec. 4].

### 3.6 Readiness and health

- From start, poll the ready URL every 250 ms (`HttpClient`, `UseProxy = false`, 1 s timeout)
  and print `still starting (Ns)` every 10 s. Stop waiting after 120 s for the server (the first
  `uv run` may sync the venv; migrations and world generation run at startup) and 30 s for the
  web: report it and keep the process, which may just be slow.
- Once ready, poll every 2 s. Three failures in a row: `down`, plus the last 15 lines of that
  service's output. A 200 again: `ready`.
- The root process exits: `exited (code N)`, the last 15 lines, and the rest of its job is
  terminated. No automatic restart; the crash stays on screen until R, W or, for the server, the
  next saved source file [Sec. 3.7].

### 3.7 Stop, restart, quit

- **Stop a service**: graceful, then hard. Graceful is `EtherBound.exe --ctrl-c <root pid>`,
  started hidden: it frees its own console, attaches to the service's, ignores Ctrl+C itself and
  sends `CTRL_C_EVENT` to that console. uvicorn runs its lifespan shutdown (clock, WebSockets,
  engine dispose); Vite exits. Wait up to 5 s for the service job to empty, then terminate it
  and say so. A service still `starting` is terminated straight away: there is nothing to shut
  down yet, and uv ignores a Ctrl+C that arrives before it has launched Python.
- **Restart** (R, W): stop, wait up to 5 s for the port to be released, start, readiness as in
  [Sec. 3.6].
- **Hot reload** (unless `--no-reload`): `FileSystemWatcher` on `server/src` and
  `server/alembic` for `*.py` and `*.toml` (the materials registry is TOML), ignoring
  `__pycache__`. After 300 ms without further changes the server restarts, and the step names
  the changed files. The next restart waits until the server has settled (ready or failed), so
  the saves made during a restart cause exactly one more. A server that crashed on broken code
  comes back with the next save.
- **Quit** (Q, Ctrl+C): stop both in parallel, then exit. A second Ctrl+C exits at once; the
  launcher job kills the rest.
- **Window closed**: `PosixSignalRegistration` for `SIGHUP` (`CTRL_CLOSE_EVENT`, through
  `SetConsoleCtrlHandler`). Windows allows about 5 s, so give the graceful stop 3 s and return;
  the launcher job does the rest.
- **The launcher job is never disposed.** Closing its handle kills every process in it, the
  launcher included, so it is held for the process's lifetime (a static field, out of the GC's
  reach) and closes when the process exits. Disposing it early turned every exit code into 0.

### 3.8 Leftovers and ports

A **leftover** is one of:

- a listener on 8000 or 5173 whose image path or command line, or those of its nearest living
  ancestor, contains `<root>\server\` or `<root>\web\`;
- part of the old launcher: a command line containing `<root>\scripts\run-server.bat`,
  `<root>\scripts\run-web.bat` or `<root>\scripts\launcher.ps1`.

Matching ignores case and treats `/` as `\`. `<root>` is this checkout, so other worktrees
(`<root>\.kilo\worktrees\...\server\`) never match. Nothing else is a leftover: the editor's
Python tooling and test runs also live in `server\.venv` and must survive. The rule is a pure
function over a process snapshot, so it is unit-tested [Sec. 8].

- On start, leftovers are killed with their tree and each kill is printed. The first run clears
  the old launcher's wrappers, PID 13848 included.
- Any other listener on 8000 or 5173 is shown (PID, name, command line) with `[K] kill it and
  continue` / `[Q] quit`. Headless, the launcher exits 1 instead.
- Lookups: `GetExtendedTcpTable` (IPv4 and IPv6 listeners) for the owner PID;
  `QueryFullProcessImageNameW` for the image; `NtQueryInformationProcess`
  (`ProcessCommandLineInformation`) for the command line; `CreateToolhelp32Snapshot` for parents.
  A "parent" created after its child is a reused PID, not the parent.
- If the owner PID no longer exists (an inherited or duplicated socket can outlive its creator),
  report it and do not guess.
- If nothing listens but a test bind fails with `WSAEACCES`, the port sits in a Windows excluded
  range: say so and name `netsh interface ipv4 show excludedportrange protocol=tcp`.
- `--cleanup` runs the leftover pass and the report only, and refuses while a launcher for this
  checkout is running (the mutex is taken).
- Before trusting the rule, check on a real run which process owns 8000 under `--reload` and that
  the rule identifies it.

- One line per event, both services interleaved, the source column coloured per source; `[FAIL]`,

  `EtherBound v0.0.1 · server ready · web ready`.

  foreign port owner makes it exit 1. Agents stop it by ending the process; the launcher job
  takes the services with it.

### 3.10 Logs

- `logs/server.log`, `logs/web.log`, `logs/launcher.log`; the previous run is kept as `*.prev.log`.
- Written by the launcher from the pipes, so no child ever holds a log open (P3). UTF-8, one
  timestamp per line, ANSI sequences stripped.
- A locked file falls back to `<name>.<yyyyMMdd-HHmmss>.log` with a warning.
- The last 200 lines per service stay in memory for the reports in [Sec. 3.6].

## 4. Traps

Each of these looks harmless and breaks something:

- **Breakaway flags on our jobs.** The server chain runs through two Python launchers (uv's
  trampoline `uvicorn.exe` and the venv `python.exe`), and both put their child in a job of their
  own. Launchers of that family allow silent breakaway, and a silent breakaway climbs every parent
  job that permits breakaway: with `BREAKAWAY_OK` or `SILENT_BREAKAWAY_OK` on our jobs, uvicorn's
  worker would leave them and outlive the launcher, holding port 8000 and the database.
- **Inheritable job handles.** A child holding a copy keeps the job alive after the launcher dies,
  and nothing gets killed.
- **`CREATE_NEW_PROCESS_GROUP`** disables Ctrl+C for the whole group, so the graceful stop would
  never reach the service. Separate consoles isolate the signal instead.
- **uvicorn's `--reload` under the launcher.** On Windows the reloader restarts its worker with
  `os.kill(worker, CTRL_C_EVENT)`, and conhost only dispatches a pending Ctrl+C when some process
  makes a console call on that console. With every stream on a pipe nothing ever does: the
  reloader waits forever and the old worker keeps serving stale code. Measured on 2026-09-22:
  window or no window, the reload hung until a third process attached to the console, and then
  it completed at once (the old launcher got away with it by accident, through its batch
  wrappers and console output). The launcher reloads by restarting the server itself
  [Sec. 3.7]. Its own `--ctrl-c` helper is not affected: attaching, signalling and detaching are
  console calls.
- **Publishing into the root** (`dotnet publish -o .`) makes the output folder an ancestor of the
  project, and the SDK then excludes the project's own sources (`CS5001`, no `Main`). Publish to
  the default folder and copy the exe.
- **`vswhere.exe` not on `PATH`.** The VS 2026 Build Tools' `vcvarsall.bat` calls it unqualified;
  its "not recognized" error lands in the output the ILCompiler parses for the linker path, and
  the link fails. `npm run launcher:build` adds the VS Installer folder to `PATH` first.
- **Closing a service's stdin** stops Vite: its dev server exits on stdin EOF
  (`process.stdin.on("end")`).
- **`FORCE_COLOR=0`** turns colour on: picocolors treats any value as "force". Use `NO_COLOR=1`.
- **Sending Ctrl+C from the launcher itself.** Attaching to another console means freeing its own,
  which destroys its window. Hence the helper process.
- **Opening the browser as a child.** If the browser was not running, it would join the launcher
  job and die on quit. `explorer.exe <target>` hands the request to the running shell and exits,
  so the browser or folder window belongs to the shell. If the acceptance test shows otherwise,
  start a small opener process before the launcher joins its job and send it the targets.
- **Missing uvicorn lines are not a launcher bug.** `server.log` goes quiet right after the
  migrations (no "Application startup complete", no shutdown lines), in the old logs too: running
  Alembic's `fileConfig` disables the loggers that already exist, uvicorn's included. It is a
  server issue, out of scope here [Sec. 10].
- **Rebuilding while it runs.** The exe is locked; quit it before `npm run launcher:build`.
- **Drift.** `<Version>` in the csproj moves with the `launcher` row of `docs/utils/VERSION.md`; if the
  `dev` script in `web/package.json` gains flags, mirror them in `Services.cs`.

## 7. What must not break

- Nothing under `server/` or `web/` changes. `uv run uvicorn ...` and `npm run dev` still work by
  hand, and the checks in `CONTEXT.md` still pass.
- Hosts and ports stay `127.0.0.1:8000` and `127.0.0.1:5173`; the Vite proxy is untouched.
- Log names in `logs/` stay.
- Every way of quitting leaves no process of this checkout behind and `data/etherbound.db`
  unlocked.
- Only this checkout's leftovers are killed without asking; other worktrees, editor tooling, test
  runs and foreign apps are never touched.
- The launcher never touches the database and talks to the server only through `GET /api/health`.

## 10. Out of scope

## TL;DR

The batch launcher fails by construction: uvicorn's hot reload sends Ctrl+C to its whole console,
the hidden `cmd.exe` wrapper turns it into a "Terminate batch job?" prompt nobody can answer, the
cleanup patterns miss that wrapper, and the leftover (PID 13848, alive since last night) keeps
`server.log` locked, so today's run never started the server while the launcher printed `[ OK ]`.
`EtherBound.exe` replaces it: a Native AOT C# console app on .NET 10 that starts `uv` and Vite's
`node` entry directly with no shells, gives each service a hidden console and a job, sits in a
kill-on-close job itself so no way of quitting leaves zombies, checks health instead of assuming
it, clears this checkout's leftovers and asks before touching anything else, and writes clean
UTF-8 logs. Hot reload comes back, driven by the launcher: uvicorn's own reloader hangs when its
output is piped. `start.bat`, `cleanup.bat` and `scripts/` go; `launcher` lands on v0.0.1 and
`tooling` moves to v0.0.8.
