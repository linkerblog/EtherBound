# Dev-003: Event bus faults are visible and bounded

[Bugfix] [Events] [Engine]

The event bus swallows two kinds of fault without a trace. A handler that throws is appended to
`EventBus.Failures`, which nothing in production reads and nothing ever trims. A cascade that
reaches `MaxCascade` clears the queue and returns, with no record that events were dropped. Both
break the promise that a run can be understood from its seed and its log. This change keeps the
bus's forgiving behavior (one bad handler never stops the tick) but makes every fault counted,
bounded in memory and reachable by the host and by tests.

## 1. Findings

Read from the source; nothing here was measured or run.

- `Events/EventBus.cs`: `Failures` is a plain `List` that only grows. Its only readers are tests
  (`EventBusDispatch.cs`, `ActionScenarios.cs`). In an endless run with a handler that throws once
  per tick, it holds every exception and its event for the whole session.
- `Drain()` stops at `dispatched >= MaxCascade`, calls `_queue.Clear()` and returns. Logged events
  were already stamped and persisted by `WorldEngine.Publish`, so the log says they happened while
  no subscriber ever saw them. Sim state that depends on handlers then drifts from the log.
- The truncation is covered by `A_self_feeding_cascade_stops_at_the_limit`, which asserts only the
  stop, not that anything reports it.
- The host has a `Fault` property for a dead sim thread but no channel for bus faults.

## 2. Decisions

Marked **approval needed** where the choice is open.

- **D1. Keep isolation.** A throwing handler still does not stop other handlers or the tick.
  Settled: this is existing, tested behavior.
- **D2. Bound the failure list.** Keep the last 64 failures and a monotonic `FailureCount`.
  Approval needed: the size (64 is a proposal, not a measurement).
- **D3. Record truncation.** On reaching `MaxCascade`, still clear the queue (the tick must end),
  but store a `CascadeStop` with the event type being dispatched and the number of dropped events,
  and increment `CascadeStopCount`.
- **D4. Strict mode.** `EventBus.Strict` (default `false`) rethrows a handler failure and throws
  on a cascade stop, so test worlds fail loudly. Approval needed: whether the shipped client should
  ever enable it. Proposal: tests only.
- **D5. Host exposure.** `SimulationHost` exposes `BusFaultCount` (failures plus cascade stops) as a
  read-only value, so the client can show a debug indicator later. No UI is added here.

## 3. Changes

### 3.1 `sim.events`

- `Failures` becomes a bounded read-only view of the last 64 entries; add `FailureCount`.
- Add `CascadeStop` record and `LastCascadeStop`, `CascadeStopCount`.
- Add `Strict` behavior from D4. The bus stays free of clocks and randomness (`BannedSymbols.txt`).

### 3.2 `sim.host`

- Publish `BusFaultCount` from the sim thread with `Volatile.Write`, read with `Volatile.Read`,
  like `LatestFrame`. No new locks.

### 3.3 Tests

- Extend `sim/EtherBound.Sim.Tests/EventBusDispatch.cs`; no new file, no DEV name in any test.
- Build the shared engine fixture with `Strict = true` so an unexpected handler failure fails the
  scenario that caused it, instead of surfacing as a later `Assert.Empty(Failures)`.

## 4. What must not break

- FIFO dispatch, phase ordering and the re-entrant drain rule
  (`Wildcard_and_specific_handlers_run_in_subscription_order`, `Phases_order_systems_regardless_of_subscription_order`,
  `Reentrant_drain_returns_and_the_outer_drain_stays_fifo`).
- A failing handler is recorded and the remaining handlers still run in non-strict mode.
- Determinism: same seed and commands give the same events, sequence numbers and log. Counters
  must not feed back into any decision.
- The 1,000-Extra Release benchmark stays within its current gate (`sim/EtherBound.Bench`). The
  bus adds two integer increments on the fault path only.
- Save compatibility: no schema change, no migration.

## 5. Acceptance

- **A1.** After 1,000 failing dispatches, `Failures.Count` is 64, `FailureCount` is 1,000 and the
  retained entries are the last 64. Verified by `EventBusDispatch.cs`.
- **A2.** A cascade that hits `MaxCascade` sets `LastCascadeStop` with the pending event type and
  a dropped count equal to the queue length at the stop, and `CascadeStopCount` is 1. Verified by
  `EventBusDispatch.cs`.
- **A3.** With `Strict = true`, a throwing handler and a cascade stop each throw; with the default,
  neither throws. Verified by `EventBusDispatch.cs`.
- **A4.** `SimulationHost.BusFaultCount` equals `FailureCount + CascadeStopCount` after a scripted
  failure, read from the client thread. Verified by `HostRules.cs`.
- **A5.** Existing `ActionScenarios.cs` and the goldens pass unchanged. Verified by
  `npm run check:sim`.
- **A6.** Bench gate unchanged. Verified by `npm run check` (manual: compare the average tick with
  the last recorded 64.864 ms, since the bench is timing-dependent and cannot be a pass/fail test).

- Input replay (commands per tick) and any change to what the event log stores.

- Any client UI for the fault counter.

## TL;DR

Handler failures and cascade truncation are currently silent and unbounded. Keep the bus
forgiving, but cap the failure list, record every cascade stop, add a strict mode for tests and
expose one fault counter through the host, with no change to event order, saves or determinism.
